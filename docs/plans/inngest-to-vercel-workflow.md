# План миграции Inngest → Vercel Workflow

Дата: 2026-09-19. Статус на 2026-09-21: локальная реализация завершена; облачное переключение и живые проверки остаются в T-08, эпик [E-004](../epics/epic_04/_index.md).

## 1. Объём и принятые решения

- Проверены **14 зарегистрированных Inngest-функций основного приложения**: **13 перенести в Workflow, `generate-comment-drafts` удалить по решению пользователя**. Инвентаризация выполнена по `lib/inngest/functions/index.ts`, всем `createFunction`, событиям, вызывающим маршрутам/actions и текущему UI.
- **Лендинг `website/` исключён по прямому ответу пользователя.** Его `deliver-early-access-lead`, зависимости, секреты и отдельное приложение Inngest сохраняются.
- Ошибка пользовательской операции сразу становится видна в UI. Повтор запускает пользователь; автоматические повторы бизнес-действия по умолчанию отключены.
- Подтверждённые исключения: Web Push и две служебные очистки допускают до двух автоматических повторов (максимум три попытки).
- Сохраняются Supabase, RLS, Realtime, адаптеры `lib/channels/`, вызовы моделей через `lib/ai`. Переносится оркестрация и обработка ошибок.
- Текущие правила архитектуры, требующие Inngest и retry для каждой отправки, при реализации заменить правилами Vercel Workflow и ручного повтора согласно этому запросу пользователя.

## 2. Короткая карта миграции

Имена справа — предлагаемые экспортируемые функции в `lib/workflows/`. Для каждой — отдельный файл в kebab-case. «0» означает отсутствие автоматических повторов бизнес-шага после ошибки, а не гарантию exactly-once со стороны инфраструктуры.

| Inngest-функция | Vercel Workflow | Что делает | Повтор после ошибки |
|---|---|---|---|
| `generate-draft` | `generateDraftWorkflow` | Создаёт AI-черновик ответа в переписке | 0; «Создать заново» в поле ответа |
| `generate-comment-drafts` | **Удалить** | Неиспользуемая генерация AI-ответов на комментарии | Не переносится по решению пользователя |
| `auto-reply` | `autoReplyWorkflow` | Ждёт паузу, выбирает сценарий и шаблон, передаёт сообщение на отправку | 0; ручной повтор в переписке |
| `send-message` | `sendMessageWorkflow` | Отправляет сообщение через адаптер и сохраняет результат | 0; «Повторить» у сообщения |
| `send-comment` | `sendCommentWorkflow` | Публикует ответ на комментарий | 0; добавить «Повторить» у ответа |
| `send-comment-private-reply` | `sendCommentPrivateReplyWorkflow` | Отправляет личное сообщение автору комментария | 0; существующая кнопка повтора |
| `send-push` | `sendPushWorkflow` | Уведомляет устройства о входящем, удаляет истёкшие подписки | До 2 повторов только неуспешной подписки |
| `contact-avatar` | `syncContactAvatarWorkflow` | Обновляет фотографию контакта | 0; «Обновить фото» при ошибке |
| `post-thumbnail` | `syncPostThumbnailWorkflow` | Загружает миниатюру опубликованного поста | 0; «Обновить миниатюру» при ошибке |
| `publication-generation` | `generatePublicationWorkflow` | Генерирует идеи, план, тексты и изображения/слайды публикации | 0; повтор только незавершённых этапов |
| `publication-import` | `importPublicationWorkflow` | Переносит изображения из ChatGPT в Storage и завершает импорт | 0; повтор импорта со свежими ссылками при необходимости |
| `publication-send` | `publishPublicationWorkflow` | Публикует выбранную версию в конкретный канал, сверяет результат | 0; «Повторить» либо «Проверить статус» |
| `cleanup-ai-request-log` | `cleanupAiRequestLogWorkflow` | Удаляет AI-логи старше 30 дней | До 2 повторов, затем сигнал оператору |
| `cleanup-publication-assets` | `cleanupPublicationAssetsWorkflow` | Удаляет неиспользуемые файлы, истёкшие OAuth grants и старые завершённые задания | До 2 повторов, затем сигнал оператору |

Особенности, влияющие на объём:

- `generate-comment-drafts` зарегистрирована, но `emitCommentDraftsRequested` не вызывается из прикладного кода. В текущем комментарном UI есть ручные ответы, шаблоны и перевод; запуска AI-черновиков не найдено. Пользователь решил удалить функцию. Удалить регистрацию, событие, неиспользуемый emitter и относящийся только к ней pipeline/тесты; общие AI/DB-хелперы проверять по ссылкам перед удалением. Исторические данные и таблицы автоматически не удалять.
- Описанная в архитектуре функция `cleanup` для старых webhook-событий не реализована и не зарегистрирована. Её создание — отдельная задача, не миграция существующей функции. Упоминание digest в комментарии к отправке push также не означает наличия такой функции.
- У обычных сообщений и private reply уже есть ручной повтор. У собственного публичного ответа на комментарий сейчас показывается результат доставки, но отдельной кнопки повторной отправки нет.
- У публикаций уже есть сохранение промежуточных этапов, повтор генерации, повтор импорта и проверка доставки. Это использовать, а не строить второй механизм.
- В `send-push-pipeline.ts` некоторые ошибки доставки логируются и проглатываются: настройка `retries: 3` не означает, что они действительно повторяются. Новая политика должна быть явной для каждой подписки.

## 4. Политика ошибок и ручных действий

### Общая схема

1. Запрос проверяет пользователя, членство в workspace и права на объект; сохраняет операцию и её входные данные в Supabase.
2. Сервер запускает workflow с идентификаторами операции и workspace. В UI появляется выполняющаяся операция.
3. Бизнес-шаг делает одну попытку. При известной неудаче сохраняет безопасный код ошибки и состояние, разблокирующее UI.
4. Ручной повтор создаёт новую попытку той же операции. Одновременные клики/вкладки схлопываются атомарно в БД.
5. Готовые этапы сохраняются. Новая попытка не повторяет успешную отправку и не генерирует заново готовые слайды.

Предусмотреть `operationId`, `attemptId`, `runId`, тип операции, ссылку на объект, статус и время обновления. Предлагается небольшая таблица `workflow_operations` с `workspace_id`, RLS и каскадом от workspace; подробный результат остаётся в существующих предметных таблицах. Согласовать статусы с имеющимися схемами, не заменять все статусы продукта единым enum без необходимости.

Ручной повтор — новый запуск с новой попыткой, а не бессрочно спящий workflow в ожидании клика. Попытка нужна также для отмены и финализации: завершение старого запуска не должно затирать результат нового.

### Неизвестный результат отправки

Таймаут внешнего запроса не доказывает, что сообщение или пост не отправлен. Поэтому:

- отделить подтверждённую ошибку от состояния «Результат отправки неизвестен»;
- использовать стабильный ключ бизнес-операции там, где адаптер поддерживает идемпотентность; новый workflow run не должен менять этот ключ;
- прежде чем повторять, сверить provider ID, webhook-подтверждение или доступный API статуса;
- если надёжная сверка невозможна, предложить проверку в канале и явное действие после проверки; не выполнять слепую повторную отправку;
- после успеха провайдера и ошибки записи БД восстанавливать статус, не отправлять заново;
- проверка статуса публикации не должна сама вызывать provider retry. Сейчас эти действия совмещены в `runPublicationDelivery`, поэтому их нужно разделить;
- состояние `uncertain` уже есть у публикаций; для DM, ответов на комментарии и private reply аналогичную семантику добавить миграциями или через связанную операцию.

Отключение retry в SDK не отменяет необходимость этих защит: остаются дубли запуска, перезапуски инфраструктуры и повторные клики.

### Фоновые исключения — подтверждено пользователем

- **Web Push:** до двух автоматических повторов временной ошибки по конкретной подписке, с ограниченным сроком актуальности уведомления. Успешные устройства не уведомлять повторно. 404/410 — удалить подписку, не повторять. Кнопка «повторить уведомление о сообщении» практически бесполезна.
- **Очистки:** до двух повторов временной ошибки конкретного безопасного шага; постоянная ошибка → сигнал обслуживающему оператору. Следующее выполнение по расписанию сохраняется. Удаление по возрасту и очистка Storage должны быть идемпотентными и идти ограниченными партиями.
- **Аватары/миниатюры:** без автоматического retry. Различать «фото нет у провайдера» и «загрузка сломалась»; кнопку показывать при ошибке. Новое входящее может снова запросить отсутствующий/устаревший ресурс, как сейчас.
- **Техническая фиксация состояния:** допустим ограниченный повтор записи ошибки/результата в БД, не содержащий повторного вызова LLM или отправки. Иначе сбой БД лишит пользователя самой возможности увидеть ошибку.

### Автоответ

Подтверждено пользователем: без автоматического повторного вызова модели или отправки. До создания сообщения ошибка видна в переписке как «Автоответ не выполнен» с действием «Повторить автоответ»/возможностью ответить вручную. После создания сообщения используется обычный UI его доставки и повтора.

При ручном запуске заново проверить последнее входящее, отсутствие ответа оператора, актуальность настроек, окно ответа канала и защиту от повторения сценария. Сохранить существующую паузу от последнего входящего через durable sleep. Сон не считается retry. Не удерживать блокировку workspace/conversation во время сна.

Сейчас журнал автоответа записывает `sent` после постановки сообщения на отправку. При миграции разделить «передано на отправку» и подтверждённую доставку, опираясь на связанную строку сообщения.

## 5. Изменения по функциональным группам

### Черновики ответов

- `generateDraftWorkflow`: загрузка контекста, маскирование, вызов модели и сохранение результата через существующую логику. Ошибка → `failed`, поле ответа разблокировано, доступно повторное создание.
- Кнопка «Стоп» сначала отменяет конкретную попытку в БД, затем отменяет run доступным API выбранной версии Workflow SDK. Перед записью результата — повторная проверка попытки. Уже начатый внешний вызов нельзя считать гарантированно прерванным.
- `generate-comment-drafts` удалить вместе с неиспользуемым запуском; нового workflow для неё не создавать. Ручные ответы на комментарии, шаблоны и переводы сохраняются.

### Сообщения и ответы на комментарии

- Перенести три отправки на отдельные workflow с общими шагами учёта попыток и безопасного результата.
- Сохранить порядок отправки в одной переписке/под одним постом, ограничения workspace, адаптеры и повторные проверки доступа/подключения.
- Для `send-comment` добавить server action и кнопку повторной отправки **существующего ответа**, без создания второго комментария в БД.
- Для private reply повторно проверять доступность операции и окно ответа; если исправление невозможно, объяснять причину вместо неработающей кнопки.
- `autoReplyWorkflow` использует тот же механизм `sendMessageWorkflow`; регистрация дочерней отправки должна быть идемпотентной. Ошибка запуска отправки не оставляет сообщение навсегда в `pending`.

### Публикации

- `generatePublicationWorkflow`: сохранить идеи, outline, текст, отдельное изображение и карусель. Каждый затратный этап сохраняет результат в Supabase; пользователь повторяет только незавершённое. Сохраняются проверки редакции, автора и выбранного контекста. Готовый результат старой попытки не перезаписывает новую редакцию.
- `importPublicationWorkflow`: учитывать текущую границу 270 секунд и временные ссылки. Сохранить ограниченную параллельность загрузок, вынести прогресс отдельных файлов в checkpoint. После истечения ссылок требовать свежий импорт через существующий UI; повтор со старой ссылкой не поможет. Байты и URL не возвращать из workflow steps.
- `publishPublicationWorkflow`: единица работы — одна delivery конкретного канала. Подготовка медиа, отправка и фиксация результата разделены. Для успешного канала действие не повторяется из-за ошибки другого канала. Сохранить существующую защиту по `first_sent_at`, remote ID и сроку идемпотентности провайдера; перед реализацией подтвердить контракт адаптера. «Проверить статус» — только чтение и сохранение результата.

### Очистки и изображения

- Два Vercel Cron endpoint запускают соответствующие workflow: AI-логи ежедневно в **03:00 UTC**, очистка публикаций каждый час на **17-й минуте UTC**. Endpoint защищён `CRON_SECRET`; повторная доставка одного расписания безопасна.
- AI-логи: сохраняется 30-дневная ретенция и фиксированный cutoff одной попытки очистки.
- Публикации: удаляются пути `publication_orphan_paths`, связанные метаданные, истёкшие `gpt_oauth_grants`, завершённые imports и generation jobs старше 30 дней. Не удалять активные задания и файлы, на которые ссылаются живые публикации.
- Аватары/миниатюры: сохраняются проверки свежести и наличия картинки; добавить безопасные UI-операции обновления, состояние ошибки и дедупликацию.

## 6. Технический фундамент Vercel Workflow

1. Зафиксировать подходящую версию пакета `workflow`. Проверить Next.js 16.2.10, `next build --webpack`, обёртку Serwist, dev через Turbopack и ограничения длительности шагов с генерацией изображений.
2. Добавить интеграцию SDK в `next.config.ts`; проверить сгенерированные workflow/step routes, `proxy.ts` и `app/sw.ts`: служебные запросы не должны получать login redirect или попадать в offline-кэш. При этом пользовательские start/status/retry/cancel endpoints остаются авторизованными.
3. `lib/workflows/` содержит оркестрацию с `"use workflow"`, отдельные функции с `"use step"` и серверный слой запуска. Зависимую от Node.js/БД/провайдера логику выполнять внутри steps. Не переносить механически `step.run` с произвольными замыканиями.
4. У бизнес-шагов явно `maxRetries = 0`; постоянные ошибки классифицировать через поддерживаемый SDK `FatalError` либо безопасный результат ошибки. У разрешённых фоновых шагов явно задать лимит и задержку. Проверить отсутствие скрытых повторов в HTTP/LLM-клиентах; у текущих AI-клиентов уже `maxRetries: 0`.
5. Не предполагать прямой эквивалент Inngest `concurrency`/`cancelOn`. При выборе SDK проверить доступные API. Для обязательных гарантий использовать атомарные RPC, уникальные ключи и ограниченные по времени блокировки с идентификатором владельца в Supabase. Сохранить общий смысл текущих лимитов workspace и последовательность по сущности; проверить разделяемость ключей между разными workflow.
6. Во входах/выходах workflow и steps — только ID и минимальные технические статусы/счётчики. Контекст, текст, адреса, токены, временные URL и байты остаются внутри шага и Supabase. Текущие `load-context` steps нескольких Inngest-пайплайнов возвращают контент; эти границы нужно переделать, а не копировать.
7. Ошибки и логи санитизировать: не сериализовать тело ответа провайдера, промпты, push endpoints и credentials в историю Workflow.
8. Настроить **и выполнение функций, и хранение состояния workflow в `fra1`**. Официальная документация на дату аудита указывает multi-region начиная с `workflow 5.0.0-beta.33`; запуски линии 4.x хранятся в `iad1`. Поэтому нельзя установить произвольный latest/stable и считать регион вопросом только Next.js. Проверить актуальную версию и фактический регион тестового run перед запуском в production.
9. Обновить архитектуру и описание обработки данных: Vercel теперь хранит историю оркестрации. Удаление Inngest из продуктового контура не означает удаления Inngest из описания отдельного лендинга.

Документированные основы: [Vercel Workflows — регионы и хранение состояния](https://vercel.com/docs/workflows), [Workflows, steps и sleep](https://vercel.com/docs/workflows/concepts), [настройка `maxRetries`, включая 0](https://vercel.com/academy/svelte-on-vercel/workflow-error-handling), [защита и эксплуатация Cron Jobs](https://vercel.com/docs/cron-jobs/manage-cron-jobs). Точные API отмены, ограничения параллельности, ретенцию и совместимость сборки проверять на закреплённой версии SDK в техническом прототипе.

## 7. Ошибка запуска и зависшие операции

Отдельно покрыть сбой **до** старта workflow и аварийное завершение без возможности выполнить обработчик ошибки.

- Сначала зарегистрировать операцию в БД. Если `start()` не принят — пометить её ошибкой и дать ручной повтор. При неизвестном результате старта два run не должны одновременно получить право исполнить бизнес-шаг.
- Для webhook-инициированных операций зарегистрировать намерение вместе с сохранением данных, насколько позволяет текущая транзакционная граница. Входящее сообщение остаётся успешно принято даже при недоступности Workflow; проблему фоновой операции можно восстановить по записи намерения.
- Не запускать бизнес-работу произвольным fire-and-forget после HTTP-ответа. Проверить время подтверждения запуска и сохранить требование быстрых webhook-ответов.
- При открытии/обновлении UI сервер сверяет просроченную активную операцию с run и блокировкой. Завершившийся/не стартовавший run приводит к видимой ошибке; ещё работающий run не перезапускается по одному лишь таймауту браузера.
- Для операций без UI выполнять такую же сверку служебным проходом в рамках фонового обслуживания; retry только по разрешённой политике.
- Сбой записи статуса после внешней отправки приводит к проверке результата, не к новой отправке. Старые попытки не могут финализировать/отменить новую.

## 8. Порядок реализации после согласования

1. **Технический прототип и контракты.** Закрепить SDK, регион, интеграцию сборки, поведение `maxRetries = 0`, запуск/отмену и границы сериализации. Проверить ограничения Vercel-тарифа для почасового Cron и длительных steps. Результат — подтверждённая конфигурация и схема операции.
2. **Миграции БД и общий UI ошибок.** Учёт попыток, дедупликация, блокировки, неизвестный результат отправки, устранение зависших статусов, start/retry/cancel/status с RLS-проверками.
3. **Отправки.** `send-message`, `send-comment`, `send-comment-private-reply`; ручной повтор и проверка неопределённого результата. Автоответ пока может вызывать общий слой отправки через выбранный движок.
4. **AI и автоответ.** Перенести `generate-draft` и `auto-reply`; паузы, отмена и журнал результатов. Удалить неиспользуемую `generate-comment-drafts` и её отдельные зависимости.
5. **Публикации.** Генерация с checkpoint, импорт, отправка и отдельное действие проверки статуса.
6. **Оставшиеся фоновые задачи.** Push, аватары, миниатюры, две очистки с Vercel Cron.
7. **Переключение и удаление Inngest из основного приложения.** Обновить документацию и пройти полный smoke. Каждый этап реализуется и проверяется последовательно в согласованном эпике; текущий документ сам по себе не меняет статусы эпиков.

Переключение делать через серверный слой запуска с выбором движка для типа операции. Каждая операция закреплена за одним движком; нельзя параллельно отправлять её и в Inngest, и в Workflow. Уже принятые Inngest-запуски завершить или отменить и сверить их предметные статусы перед переносом. Особенно проверить спящие автоответы и незавершённые отправки.

При откате маршрутизировать только новые операции обратно; существующие Workflow run не исчезают от отката deployment. Остановку/дренирование и сверку выполнять явно. Не удалять deployment, на котором ещё исполняются нужные run.

После дренирования удалить основной `/api/inngest`, клиент, события, регистрации, SDK-импорты ошибок и зависимость; обновить lockfile, тесты и локальный dev-процесс. Перенести повторно используемую бизнес-логику из каталога `lib/inngest/` в предметные модули. Удалить только секреты/подключение Inngest основного Vercel-проекта. `website/` не менять.

Обновляемые документы: `AGENTS.md`, актуальные архитектурные главы 03/07/11/12/13/14/15/18 и ссылки в других главах, `README.md`, `.env.example`, `app/privacy/page.tsx`, актуальные инструкции интеграций. Исторические отчёты эпиков не переписывать так, будто Inngest никогда не использовался.

## 9. Проверки при реализации

- Из 14 строк карты 13 мигрированы, `generate-comment-drafts` удалена по решению пользователя.
- Для пользовательских бизнес-шагов ошибка приводит ровно к одной попытке провайдера/LLM; повтор начинается только после действия пользователя.
- Двойной клик, две вкладки, повтор доставки start и повтор run не создают две внешние отправки. Порядок сообщений и лимиты workspace сохраняются.
- Успех провайдера + сбой БД, таймаут отправки и запоздалый webhook не превращаются в слепую повторную отправку.
- Ошибка start, аварийное завершение и неуспешная запись `failed` не оставляют UI заблокированным навсегда.
- Stop, новое входящее и ответ оператора корректно останавливают/делают неактуальным старый автоответ/черновик.
- Повтор генерации карусели сохраняет готовые слайды; повтор импорта после истечения URL требует свежие файлы; проверка статуса поста не публикует его повторно.
- Частичная ошибка Push не повторяет успешные подписки; очистки повторяемы и защищены от пересечений.
- RLS: другой workspace не может запускать, читать статус, повторять или отменять операцию. В истории Workflow нет содержимого сообщений и секретов.
- `lint`, TypeScript/build, соответствующие unit/интеграционные тесты и smoke после каждой фичи; итоговый smoke «вебхук → инбокс → черновик → ошибка отправки → ручной повтор», плюс публикация и отмена автоответа на staging.
- После переключения в основном продукте отсутствуют рабочие SDK-импорты/вызовы Inngest, оба Cron запускаются в Vercel, фактический регион проверен. Исключения поиска — историческая документация и отдельный `website/`.
