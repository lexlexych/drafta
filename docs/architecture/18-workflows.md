# 18. Durable-исполнение: Vercel Workflows

> [!info] Навигация
> ⬅️ [14. Правила вайбкодинга](14-vibecoding-rules.md) · ⬆️ [Оглавление](_index.md) · ➡️ [15. Compliance: GDPR](15-compliance-gdpr.md)

Вся фоновая работа проекта — генерация черновиков, отправка наружу, пуши,
дочитывание аватаров и обложек, ночная чистка логов — идёт **прогонами**
(workflow runs) поверх [Vercel Workflows](https://vercel.com/docs/workflows) и
открытого [Workflow SDK](https://workflow-sdk.dev). Отдельного оркестратора у
проекта нет: исполняемый код живёт в том же Next.js-проекте, а платформа даёт
durable-исполнение — прогон переживает падение инстанса, деплой и ретраи.

## Модель

Две директивы превращают обычные async-функции в durable-код.

**`"use workflow"` — тело прогона.** Оркестратор: вызывает шаги, ветвится,
крутит циклы, ждёт. Исполняется в детерминированной песочнице с урезанным Node
API и **проигрывается заново** после каждой приостановки, подставляя уже
записанные результаты из журнала событий. Отсюда правило: в теле прогона нет
ни обращений к БД, ни сетевых вызовов — только композиция шагов.

**`"use step"` — единица работы.** Полный рантайм Node, любые пакеты, доступ к
Supabase и внешним API. Каждый шаг ретраится независимо, а его результат
записывается в журнал: повторный проигрыш прогона шаг не переисполняет.

```ts
// lib/workflows/media/post-thumbnail.workflow.ts
export async function postThumbnailWorkflow(input: PostThumbnailInput) {
  "use workflow";

  const leases = [entityLease("post", input.postId, input.workspaceId)];
  await acquireLeases(leases);
  try {
    const loaded = await loadPostThumbnailContext(input);   // шаг
    if (loaded.status === "skip") return { status: "skipped", reason: loaded.reason };
    return { status: await fetchAndSavePostThumbnail({ ... }) };  // шаг
  } finally {
    await releaseLeases(leases);
  }
}
```

Поэтому каждый прогон живёт в двух файлах: `<имя>.workflow.ts` — тело,
`<имя>.steps.ts` — шаги. Разделение не косметическое: оно физически не даёт
затащить серверный код в песочницу.

> [!tip] Детерминированные примитивы
> `Date`, `Date.now()`, `Math.random()` и `crypto.randomUUID()` внутри тела
> прогона зафиксированы: при повторном проигрыше они отдают те же значения.
> Поэтому отметку времени можно взять прямо в теле, отдельный шаг ради
> стабильного «сейчас» не нужен.

## Запуск

Единственная точка запуска — **`lib/workflows/start.ts`**. Снаружи видны только
её обёртки; ни один экран и ни один роут не зовёт `start()` напрямую.

Каждая обёртка явно выбирает границу отказа:

| Граница | Кто так запускается | Почему |
|---|---|---|
| **Проглатывает ошибку** | `send-push`, `contact-avatar`, `post-thumbnail` | Вызывающий — вебхук-роут: сообщение уже сохранено, роут обязан ответить 200 быстрее секунды (правило 6) и не может ставить свой ответ в зависимость от фоновой задачи. Пропущенный пуш добирает дайджест. |
| **Падает** | `generate-draft`, `send-message`, `send-comment`, `send-comment-private-reply`, `comment-drafts` | Вызывающий — серверное действие, которое уже сохранило строку как `pending` или заблокировало поле ввода. Если прогон не стартовал, отправить или сгенерировать не сможет никто, поэтому действие обязано узнать о провале, компенсировать в `failed` и показать «Повторить». |

> [!danger] Правило 7 живёт в этом файле
> **Аргументы запуска — только идентификаторы**, никогда тексты сообщений,
> имена или другие персональные данные. Типы аргументов в `start.ts` и есть
> enforcement: лишнее поле — ошибка компиляции. Контент прогон дочитывает из
> Supabase сам, в момент исполнения.

## Ретраи и ошибки

Шаг ретраится автоматически: по умолчанию 3 раза (4 попытки), настраивается
свойством на функции шага.

```ts
sendMessageViaAdapter.maxRetries = 4;
```

| Что бросить | Поведение |
|---|---|
| Обычную ошибку | Шаг ретраится, пока не кончится `maxRetries` |
| `FatalError` | Ретраи отменяются, ошибка сразу уходит в тело прогона |
| `RetryableError(msg, { retryAfter })` | Ретрай с явной задержкой |

Окончательные отказы провайдера классифицирует
**`lib/workflows/send-errors.ts`**: любой HTTP 4xx, кроме 408 и 429 (истёкшее
24-часовое окно WhatsApp, ограничение платформы, кривой ID диалога) —
`FatalError`, всё остальное ретраится.

### Компенсации вместо хука на провал

Отдельного хука «прогон окончательно упал» в SDK нет, и он не нужен: когда
ретраи шага исчерпаны, ошибка доходит до тела прогона обычным исключением.
Значит компенсация — это `try/catch`, а освобождение ресурсов — `finally`:

```ts
try {
  ...
} catch (error) {
  await markMessageSendFailedStep({ workspaceId, messageId });  // «Повторить» в треде
  throw error;
} finally {
  await releaseLeases(leases);
}
```

Компенсация сама объявлена шагом — откат должен быть таким же durable, как и
работа, которую он откатывает.

Эти контракты проверяются не на словах:
`lib/workflows/runtime-contracts.integration.test.ts` гоняет настоящие прогоны и
фиксирует, что ретраи считаются как обещано, `FatalError` их отменяет, а
`catch` и `finally` отрабатывают в обоих случаях.

## Конкурентность: лизы

> [!warning] Временное решение
> Нативного примитива конкурентности в Workflow SDK пока нет (`lock()` заявлен
> в план v6), а до него официальная рекомендация — принести свой семафор поверх
> общего хранилища. Когда примитив выйдет, `lib/workflows/leases.ts`, таблица
> `public.workflow_leases` и обе RPC удаляются, а вызовы заменяются на него.

Модель простая: на ключ заведено ровно `limit` слотов, слот — строка в таблице.
Гонку разрешает первичный ключ `(key, slot)`: проигравший берёт следующий
свободный, а если свободных нет — ждёт в теле прогона через `sleep()`, что не
тратит компьют. Превысить лимит нельзя ни при какой гонке.

| Ключ | Лимит | Зачем |
|---|---|---|
| `workspace:<id>` | 2 | Бюджет LLM воркспейса: сколько генераций одного тенанта идут параллельно |
| `workspace-send:<id>` | 2 | Внешние отправки одного тенанта |
| `workspace-push:<id>` | 4 | Web Push — вызов лёгкий, лимит шире |
| `conversation:<id>`, `post:<id>`, `contact-identity:<id>` | 1 | Взаимоисключение: один прогон на сущность, плюс порядок отправки |
| `cron:<имя>` | 1 | Синглтон крона: пока прошлый обход жив, следующий тик уходит ни с чем |

Две детали, без которых это не работает:

- **Идемпотентность по `holder`.** Владелец слота — `runId`. Повторный захват
  тем же прогоном (ретрай шага, повторный проигрыш) продлевает уже занятый
  слот, а не забирает второй.
- **TTL.** Слот освобождается сам, если прогон умер, не дойдя до `finally`:
  снятый через `run.cancel()` прогон останавливается на границе шага и до
  освобождения может не добраться. Просроченные слоты вычищаются лениво, при
  следующем захвате того же ключа.

Несколько лиз захватываются строго в объявленном порядке — одинаковый порядок у
всех вызывающих исключает взаимную блокировку; если один из ключей так и не
освободился, уже занятые слоты набора отпускаются, а прогон падает.

## Отмена

Кнопка «стоп» под спиннером генерации:

1. действие переводит черновик в `discarded` — **именно это** разблокирует поле
   ввода во всех открытых вкладках, через realtime-подписку на `drafts`;
2. тот же запрос возвращает `drafts.workflow_run_id` — его записал первый шаг
   прогона;
3. действие зовёт `getRun(runId).cancel()`.

Снятие прогона идёт **вторым** и намеренно fail-safe: пользовательская отмена
уже произошла в БД, а `cancel()` лишь экономит остаток работы. Прогон мог
завершиться сам между двумя запросами — это не ошибка, о которой пользователю
надо что-то делать.

Прогон останавливается на ближайшей точке приостановки, то есть на границе
шага: уже улетевший запрос к провайдеру доработает, но до `finalize` дело не
дойдёт.

## Кроны

Расписание живёт в `vercel.json`, а не в коде функции:

```jsonc
"crons": [
  { "path": "/api/cron/push-digest",             "schedule": "*/5 * * * *" },
  { "path": "/api/cron/cleanup-ai-request-log",  "schedule": "0 3 * * *" }
]
```

Роуты под `app/api/cron/` тонкие: проверяют `CRON_SECRET`, запускают прогон и
сразу отвечают его `runId`. Работа идёт durable и переживает таймаут роута.
Перекрытие тиков гасит лиза `cron:<имя>` **внутри** прогона, поэтому роутам
ничего проверять не нужно.

> [!warning] `*/5` требует тарифа Pro
> На Hobby кроны Vercel ограничены одним запуском в сутки, и более частое
> выражение не проходит деплой.

## Регион и данные прогонов

Прогоны **явно** пиннятся в `fra1`:

```ts
await start(sendMessageWorkflow, [args], { region: "fra1" });
```

Без этой опции регион берётся из `VERCEL_REGION` вызывающей функции, а если его
нет — из серверного умолчания `iad1`, то есть США. Регион фиксируется в момент
создания прогона и не меняется задним числом.

> [!danger] Что реально лежит в журнале прогона
> Durable-исполнение устроено так, что в журнал попадают **входы и выходы
> каждого шага**, а не только аргументы запуска. Для генерации черновика это
> означает тексты переписки и ответ модели. Правило «только ID» ограничивает
> аргументы запуска и остаётся в силе — но оно не описывает журнал, и делать
> вид, что описывает, нельзя. Подробности и меры — [§15.2](15-compliance-gdpr.md#122-субпроцессоры-и-данные).

Данные прогонов шифруются, ретенция после завершения — 7 дней на тарифе Pro.
Доступ к расшифрованным данным есть у владельцев команды и у роли
«Workflow Run Data Viewer».

## Локальный контур и тестирование

Локально ничего дополнительно поднимать не нужно: `next dev` исполняет прогоны
через Local World, состояние лежит в `.workflow-data/`.

```powershell
pnpm exec supabase start
pnpm dev
pnpm exec workflow web          # веб-инспектор прогонов
pnpm exec workflow inspect runs # то же в терминале
```

Тесты разделены на два контура:

| Контур | Команда | Что проверяет |
|---|---|---|
| Юниты | `pnpm test` | Логику шагов и оркестрацию. Без компилятора директивы — no-op, поэтому шаги и тела прогонов вызываются как обычные функции, а соседний модуль шагов подменяется `vi.mock`. |
| Прогоны | `pnpm test:workflows` | Поведение рантайма: ретраи, `FatalError`, компенсации, отмену. Плагин `@workflow/vitest` компилирует директивы и поднимает Local World в процессе теста. |

Две особенности интеграционного контура, о которые легко споткнуться:

- **`vi.mock` не достаёт до шагов** — плагин исполняет их из отдельно
  собранного бандла. Наблюдать за шагом можно только через его возвращаемое
  значение и ошибку, которые идут через журнал событий.
- **Workflow-функции нельзя объявлять в тест-файле** — плагин утащит в бандл и
  сам `vitest`. Фикстуры живут отдельным модулем
  (`lib/workflows/__fixtures__/`).

## Структура

```
lib/workflows/
├── start.ts                     # запуск и отмена — единственная точка входа
├── leases.ts                    # семафор конкурентности (временный шим)
├── send-errors.ts               # классификация отказов провайдера
├── cron-auth.ts                 # проверка CRON_SECRET
├── drafts/                      # generate-draft, comment-drafts
├── outbound/                    # send-message, send-comment, send-private-reply
├── push/                        # send-push, digest
├── media/                       # contact-avatar, post-thumbnail
└── maintenance/                 # cleanup-ai-request-log

app/api/cron/<имя>/route.ts      # тики расписания из vercel.json
app/.well-known/workflow/        # служебные роуты, генерируются сборкой
```

Служебные роуты `withWorkflow()` создаёт при сборке, они не коммитятся и
исключены из матчера в `proxy.ts`: перехват `POST /.well-known/workflow/v1/flow`
ломает возобновление прогонов.
