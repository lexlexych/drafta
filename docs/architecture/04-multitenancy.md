# 4. Мультитенантность, роли, приглашения

> [!info] Навигация
> ⬅️ [3. Стек](03-stack.md) · ⬆️ [Оглавление](_index.md) · ➡️ [5. Слой абстракции каналов](05-channels.md)

Тенант — **workspace** (см. [глоссарий](02-glossary.md)).
Пользователь может состоять в нескольких workspace'ах.

## Роли

На MVP роли две:

- **owner** — единственный на workspace: биллинг, подключение/отключение каналов,
  приглашения, удаление workspace.
- **member** — работа в инбоксах, отправка ответов, редактирование базы знаний и контактов.

Передача владения — поле в схеме есть, UI отложен.

## Приглашения

**Через Supabase Auth, свой код отправки не пишем.**

Поток:

1. owner вводит email
2. создаётся запись `invitations` (workspace, роль, токен, срок)
3. вызывается `inviteUserByEmail()` из Supabase Auth Admin API с redirect на страницу приёма приглашения
4. Supabase сам отправляет письмо **через Postmark, подключённый как custom SMTP**
   (настройка в дашборде, кода нет — см. [3. Стек](03-stack.md))
5. человек проходит по ссылке, задаёт пароль
6. страница приёма находит `invitations` по email/токену и создаёт `workspace_members`

> [!important] Зачем нужна таблица `invitations`
> `inviteUserByEmail` создаёт пользователя *в системе*, но не знает, *в какой workspace
> и с какой ролью* он должен попасть — это наша ответственность.
> Схема таблицы — [6. Модель данных](06-data-model.md#invitations).

### Краевой случай: приглашённый уже зарегистрирован

Если человек уже состоит в другом workspace, `inviteUserByEmail` не подходит.

- **На MVP:** показать owner'у ссылку-приглашение «скопировать и отправить самому».
- **Позже:** отдельный прогон `notify-existing-user`, шлющий обычное письмо-уведомление
  через Postmark API — см. [6.6. Список прогонов](07-data-flows.md#66-полный-список-прогонов).

### Бонус настройки

Подключение custom SMTP чинит и остальные auth-письма (подтверждение регистрации, сброс пароля),
а верифицированный домен с DKIM переиспользуется email-каналом на
[этапе 11](16-rollout-plan.md#этап-11-после-запуска--email-канал-2-3-дня).

## Изоляция данных

`workspace_id` в каждой таблице + RLS-политики «пользователь видит строки только тех
workspace'ов, где он участник».

Серверный код (вебхуки, шаги прогонов) работает через `sb_secret_`-ключ **мимо RLS**
и фильтрует по `workspace_id` сам.

> [!danger] Следствия для кода
> `SUPABASE_SECRET_KEY` — только в серверном коде, никогда в клиентском бандле
> ([13. Секреты](13-environments-secrets.md)).
> Каждая новая таблица создаётся сразу с `workspace_id`, RLS и каскадным удалением
> ([14. Правила](14-vibecoding-rules.md)).
> Тесты RLS «member не видит чужой workspace» — обязательны.
