# 6. Модель данных

> [!info] Навигация
> ⬅️ [5. Слой абстракции каналов](05-channels.md) · ⬆️ [Оглавление](_index.md) · ➡️ [7. Потоки данных](07-data-flows.md)

Без SQL, по сущностям. Везде, кроме служебных таблиц, есть `workspace_id` + RLS
(см. [4. Мультитенантность](04-multitenancy.md#изоляция-данных)).

Все связи от workspace вниз — **с каскадным удалением**: «удалить workspace» стирает всё
(требование GDPR — [право на удаление, Art. 17](15-compliance-gdpr.md#123-технические-меры-уже-в-архитектуре) —
и просто гигиена).

## Тенант и доступ

### workspaces
Тенант: название, план, настройки (`settings` jsonb). В `settings.providerProfiles.<провайдер>`
хранится ID «профиля» провайдера канала для этого workspace — например, ID профиля Zernio,
под которым группируются подключённые аккаунты (создаётся до записи workspace,
[5. Подключение аккаунта](05-channels.md#подключение-аккаунта-oauth)). Схема остаётся
провайдер-агностичной — отдельных `zernio_*`-колонок нет.

### workspace_members
Связь user↔workspace, роль (`owner` | `member`).

### invitations
Email, токен, роль, срок действия, статус.
Зачем нужна отдельно от Supabase Auth — [4. Приглашения](04-multitenancy.md#приглашения).

## Каналы

### channel_connections
Подключённый канал. **В workspace может быть не больше одного канала каждой платформы**;
это гарантирует уникальность `(workspace_id, platform)`. Каналы различаются пользовательским
именем (см. [5. Один канал каждой платформы и имена](05-channels.md#один-канал-каждой-платформы-и-имена)):

- **name** — имя, которое каналу задаёт пользователь («WhatsApp Магазин»);
  показывается во всех списках, меню и тредах ([10. UI](10-ui.md#откуда-пришло-входящее))
- провайдер (`zernio` | `postmark` | `meta`…)
- платформа (`telegram` | `whatsapp` | `instagram`…)
- внешний ID аккаунта соцсети — **приходит из OAuth-callback провайдера**, а не
  вводится пользователем ([5. Подключение аккаунта](05-channels.md#подключение-аккаунта-oauth));
  уникальность подключения — (workspace, платформа), дополнительно
  (workspace, провайдер, внешний ID)
- **capabilities** (jsonb) — см. [5. Capabilities канала](05-channels.md#capabilities-канала)
- зашифрованные credentials (пусто для Zernio — токены платформ держит сам Zernio;
  понадобится для прямого Meta App)
- статус

> [!note] Отдельной таблицы `categories` больше нет
> Категория — это запись [`kb_files`](#kb_files): одна сущность вместо двух
> ([9. Категории и база знаний](09-categories.md)). Вместе со старой таблицей
> ушли `messages.category_id` и `conversations.category_id`; беседа теперь
> хранит `matched_kb_file_ids`.

## Люди

### contacts
Человек: отображаемое имя, заметки, теги, аватар. **Намеренно отделён от канальной личности.**
Поле `avatar_url` здесь зарезервировано под аватар, заданный вручную; фото из соцсети
живёт на identity (ниже).

### contact_identities
Канальная личность контакта: платформа + внешний ID (телефон, username, email…) → ссылка на contact.
Один контакт может иметь несколько identities.

`avatar_url` — фото профиля. Оно принадлежит именно канальной личности: у одного человека
в Telegram и в Instagram фото разные, и в переписке надо показать то, что относится к
каналу этой переписки. Хранится **только ссылка**, байты не копируются: ссылки платформ
протухают, и мёртвая ссылка просто возвращает UI к инициалам. Наружу картинка отдаётся
исключительно через собственный роут `/api/avatars/[identityId]` — браузер оператора не
должен ходить в Meta ([15. Комплаенс](15-compliance-gdpr.md)).

Во входящих вебхуках фото нет (Meta его не присылает), поэтому ссылка берётся из API
провайдера — но редко: `avatar_fetched_at` хранит время последнего похода, и новый
делается **не чаще раза в месяц и только после того, как контакт написал**. Cron не нужен:
контакт, от которого ничего не приходит, не стоит нам ни одного запроса. Отметка времени
обновляется и тогда, когда фото не нашлось, иначе контакт без аватара дёргал бы API на
каждом сообщении; сохранённую ссылку пустой ответ при этом не затирает. Сам поход —
Inngest-функция `contact-avatar` ([7. Потоки](07-data-flows.md#66-полный-список-inngest-функций)).

> [!note] Склейка контактов
> На MVP каждая новая личность автоматически создаёт нового контакта; «склейка» двух контактов
> в одного — ручное действие в UI (перевесить identities, слить заметки).
> Автоматическое сопоставление по телефону/email — задел на потом, схема к нему готова.
> UI — [10. UI и навигация](10-ui.md), этап — [Этап 7](16-rollout-plan.md#этап-7--контакты-1-2-дня).

## Переписка

### conversations
Переписка (DM) — и только она. Ветки комментариев живут в собственных таблицах
(см. [Комментарии](#комментарии) ниже): у поста нет собеседника, нет 24-часового
окна и нет категории, поэтому общая таблица с дискриминатором `kind` только
заставляла каждый код-путь ветвиться.

Поля: ссылка на contact, внешний ID диалога, статус (`open` / `snoozed` / `closed`),
`last_incoming_at` (контроль 24-часового окна — см.
[6.3. Отправка](07-data-flows.md#63-отправка-ответа)), счётчик непрочитанного.

Плюс два поля, которые обслуживают экран «Сообщения»:

- **`matched_kb_file_ids`** — [категории](09-categories.md) последнего черновика:
  их называет модель в строке `CATEGORIES:`, а `finalize_draft_generation`
  перезаписывает массив целиком. Нужны, чтобы фильтр и чипы в списке диалогов не
  превращались в подзапрос по последнему черновику. Фильтр — пересечение массивов
  (`&&`), поэтому индекс GIN, а не btree; удалённая категория вычищается из бесед
  триггером `kb_files_strip_from_conversations`
- **`draft_debounce_until`** — дедлайн текущего окна
  [дебаунса](07-data-flows.md#62-дебаунс-и-генерация-черновика). Сам дебаунс живёт
  внутри Inngest-прогона, и это единственный способ показать пользователю обратный
  отсчёт; `NULL` — ни один прогон не ждёт. `conversations` уже в Realtime-публикации,
  поэтому таймер обновляется без отдельного канала

### messages
Сообщение переписки:

- направление, текст, вложения
- автор — ссылка на `contact_identity`
- статус доставки
- сырые метаданные провайдера
- уникальность по (conversation, внешний ID); у исходящего внешний ID появляется
  только после подтверждения провайдера ([6.3](07-data-flows.md#63-отправка-ответа)),
  до этого — `null`

### drafts
Черновик ответа в переписке:

- conversation
- **диапазон входящих, на которые отвечает** (первое и последнее message — из-за
  [дебаунса](07-data-flows.md#62-дебаунс-и-генерация-черновика) черновик отвечает на пачку)
- текст
- статус: `generating` | `ready` | `edited` | `sent` | `discarded` | `superseded`
- модель
- **`kb_file_ids`** — что ушло в промпт: снимок активных [категорий](09-categories.md)
  на момент генерации ([8. База знаний в промпте](08-ai-subsystem.md#база-знаний-в-промпте))
- **`matched_kb_file_ids`** — на чём модель заземлилась: категории, которые она
  назвала в строке `CATEGORIES:` ([8. Контракт ответа](08-ai-subsystem.md#контракт-ответа-categories)).
  Их же показывает панель черновика, и они же копируются на беседу
- **`manual_review_reason`** — причина, по которой ответ должен написать человек:
  модель не нашла нужных фактов в разрешённых источниках и отказалась их выдумывать
  ([8. Заземление](08-ai-subsystem.md#заземление-и-отказ-от-выдумывания)).
  `NULL` — обычный черновик; иначе текст пустой, отправлять нечего

## Комментарии

Отдельный от переписки контур: свои таблицы, свой пайплайн, своя генерация.

### posts
Пост подключённого аккаунта. Создаётся по вебхуку `post.published` — **сразу,
до первого комментария**, поэтому только что опубликованный пост уже виден в
«Комментариях». Пост, о публикации которого мы не знали, создаётся лениво при
первом комментарии под ним.

- ссылка на `channel_connection`, внешний ID поста у провайдера (ключ
  идемпотентности), текст, ссылка на публикацию, время публикации
- **бриф черновиков** — то, что пользователь вводит в окне «Черновики»:
  описание поста (что происходит на видео) и правило ответа; отметка о том, что
  бриф подтверждён, — это и есть признак «черновики для поста настроены»
- время последнего комментария и счётчик непрочитанного

### comments
Комментарий под постом — входящий или наш опубликованный ответ:

- направление, текст, вложения
- автор входящего — ссылка на `contact_identity` (**авторы под постом разные!**)
- ID родительского комментария: у ответа на ответ — комментарий-родитель,
  у нашего ответа — комментарий, на который мы отвечаем (ответ всегда
  публикуется под конкретным комментарием)
- статус доставки, сырые метаданные провайдера
- уникальность по (post, внешний ID); у исходящего внешний ID появляется только
  после подтверждения провайдера

### comment_drafts
Черновик ответа на **один** комментарий:

- post + comment, на который отвечает
- текст, статус (тот же набор, что у `drafts`), модель, использованные файлы БЗ
- живой черновик у комментария ровно один (гарантия схемы) — перегенерация
  переводит предыдущий в `superseded` в той же транзакции

> [!important] Черновик комментария не создаётся при получении комментария
> Его запускает пользователь — кнопкой «Черновики» на посте или «Создать черновик»
> под конкретным комментарием ([7.4](07-data-flows.md#64-черновики-к-комментариям)).

## Контент и служебное

### kb_files
База знаний = список **категорий** ([9](09-categories.md)): название категории,
markdown-содержимое, порядок, флаг «включён», `updated_at`. Название уникально в
рамках workspace без учёта регистра — по нему разворачивается ответ модели.
Флаг «включён» — единственный способ убрать категорию из промпта.

> [!tip] Почему markdown лежит прямо в Postgres
> Файлы маленькие, а так они попадают в бэкапы, RLS и Realtime бесплатно.
> Storage подключим, только если появятся большие вложения.

### webhook_events
Журнал сырых вебхуков: провайдер + внешний ID события (уникальны — **идемпотентность**),
payload, отметка обработки, ошибка. Это же — механизм replay при отладке
и источник фикстур для тестов адаптеров.

> [!warning] Ретенция
> Ограничена и чистится `cleanup`-cron'ом — журнал содержит персональные данные
> и не должен жить вечно ([15. Compliance](15-compliance-gdpr.md#123-технические-меры-уже-в-архитектуре)).

### push_subscriptions
Web Push подписки по пользователям — см. [11. PWA](11-realtime-pwa.md).

### notification_settings
Настройки push на пару пользователь+workspace
([11. Частота уведомлений](11-realtime-pwa.md#частота-уведомлений--настройка-пользователя)):

- режим: `instant` (push на каждое входящее) | `digest` (сводка по интервалу)
- интервал дайджеста (например, 30 минут)
- `last_digest_at` — граница «что уже вошло в прошлую сводку»

### ai_settings
На workspace: `system_prompt` и `comment_system_prompt` (редактируемые системные промпты
для черновиков переписки и комментариев), `debounce_seconds` (по умолчанию ~45–60),
выбранная модель, авто-генерация черновиков переписки вкл/выкл. Для комментариев
переключателя нет — их черновики всегда запускает пользователь.

Отдельных колонок «тон», «язык» и «подпись» нет: они оказались слишком узкими и уходили
в промпт сырым JSON, поэтому теперь прописываются прямо в тексте промпта. Дефолтные
шаблоны заданы дефолтами колонок, так что новый workspace получает их без участия
приложения; те же тексты лежат в `lib/ai/default-prompts.ts`.
Как используется — [8. AI-подсистема](08-ai-subsystem.md#системный-промпт-workspace).
