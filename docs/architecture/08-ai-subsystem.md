# 8. AI-подсистема

> [!info] Навигация
> ⬅️ [7. Потоки данных](07-data-flows.md) · ⬆️ [Оглавление](_index.md) · ➡️ [9. Категории входящих](09-categories.md)

## Клиент и выбор провайдера

**Клиент** — стандартный OpenAI-совместимый SDK; провайдер по умолчанию — **Mistral**
(`baseURL` La Plateforme, ключ `MISTRAL_API_KEY` —
см. [13. Секреты](13-environments-secrets.md#секреты-vercel-env)).

Выбор обусловлен рынком запуска: Mistral — европейская компания с обработкой в ЕС
вне американской юрисдикции, что делает цепочку субпроцессоров объяснимой в AVV,
а «данные не покидают ЕС» — аргументом продаж.

**Условия:** DPA + режим без обучения на данных клиентов (проверить актуальные условия
La Plateforme при подключении) — см.
[15. Субпроцессоры](15-compliance-gdpr.md#122-субпроцессоры-и-данные).

### Резервный провайдер — OpenRouter

Второй поддерживаемый провайдер — **OpenRouter** (fallback). API тоже
OpenAI-совместимый, поэтому это тот же клиент `lib/ai` с другим `baseURL`
(`https://openrouter.ai/api/v1`) и ключом.

**Логика выбора** — по переменным окружения, без изменений кода:

- задан `MISTRAL_API_KEY` → работаем через Mistral;
- иначе → работаем через OpenRouter: ключ `OPENROUTER_API_KEY`,
  модель по умолчанию — переменная `OPENROUTER_MODEL` (формат `vendor/model`).

Активен всегда ровно один провайдер; провайдеры не смешиваются в рамках одного
окружения. Все переменные — [13. Секреты](13-environments-secrets.md#секреты-vercel-env).

> [!warning] GDPR-оговорка для OpenRouter
> OpenRouter — американская компания и маршрутизирует запросы к сторонним
> провайдерам моделей, поэтому аргумент «обработка в ЕС» на него автоматически
> не распространяется. Для прода с данными клиентов основной вариант — Mistral;
> включение OpenRouter в проде требует выполнения действий из его строки в
> [15. Субпроцессорах](15-compliance-gdpr.md#122-субпроцессоры-и-данные)
> (DPA, no-training, фиксация нижестоящих провайдеров и регионов).

Абстракция сохраняется: модель и `baseURL` — конфигурация, поэтому
Azure OpenAI EU Data Zone (регионы Sweden Central / Germany West Central — документированная
обработка в ЕС, если понадобятся модели OpenAI) или локальная open-weight модель
для чувствительных вертикалей — это будущая настройка, не переписывание.

> [!warning] Важно при любой замене провайдера
> «EU data residency» у провайдеров часто означает только **хранение** — требовать гарантию,
> что и **инференс** выполняется в ЕС.

## Маскирование идентификаторов перед LLM

Полная анонимизация живой переписки невозможна без разрушения смысла, и GDPR требует
минимизации, а не кастрации данных — юридическую основу даёт корректная цепочка процессоров
(DPA, no-training, минимальная ретенция).

Но дешёвый слой снижения рисков закладываем: перед отправкой в промпт очевидные идентификаторы
(телефоны, email, IBAN/номера карт) заменяются плейсхолдерами `{{PHONE_1}}`
с обратной подстановкой в готовый черновик; имя контакта в промпт не передаётся,
если не нужно для ответа.

Модуль `lib/ai/masking.ts` ([12. Структура репозитория](12-repo-structure.md)),
**покрыт юнит-тестами** ([14. Правила](14-vibecoding-rules.md)).

Место в пайплайне — шаг 2 в
[7.2. Пайплайн генерации](07-data-flows.md#пайплайн-генерации): маскирование выполняется
до классификации по категориям, потому что она тоже ходит в LLM.

## Классификация по категориям

Второй потребитель LLM после генерации черновиков — присвоение каждому входящему
[сообщению](09-categories.md) категории. Один вызов на пачку сообщений после
дебаунса (письмо — поштучно). Комментарии не классифицируются: категорий у них нет.

- в промпте — список применимых категорий (название + описание-правила)
  **в порядке приоритета** и замаскированный текст входящих;
- задача модели — вернуть первую подходящую категорию, а если ни одна не подошла —
  категорию «по умолчанию»;
- низкая температура, структурированный ответ (ID категории);
- задача проще генерации — допускается младшая (дешёвая) модель Mistral.

Маскирование идентификаторов действует так же, как для генерации: классификация
получает только замаскированный текст.

Место в пайплайне — шаг 3 в
[7.2. Пайплайн генерации](07-data-flows.md#пайплайн-генерации).

## База знаний в промпте

На MVP — **без RAG**: markdown-файлы workspace ([`kb_files`](06-data-model.md#kb_files))
конкатенируются в системный промпт
в заданном порядке, с бюджетом токенов (файлы «выключаются» флагом,
при превышении бюджета — предупреждение в UI).

Для типичной базы «описание + прайс + FAQ» (десятки килобайт) современные контекстные окна
это позволяют, а качество ответов выше, чем у плохо настроенного retrieval.

> [!tip] Точка роста заложена
> Когда появятся workspace'ы с большими базами — pgvector уже есть в Supabase,
> добавится таблица чанков с эмбеддингами и шаг retrieval в пайплайне.
> Схема `drafts` уже хранит «какие файлы использовались» — это будущий датасет
> для оценки качества.

## Структура промпта переписки

1. **роль и тон** — из `ai_settings`
2. **база знаний**
3. **заметки о контакте** — без прямых идентификаторов
4. **контекст** — история диалога, *после маскирования*
5. **правила канала** — из [capabilities](05-channels.md#capabilities-канала): длина, стиль
6. **действие категории** — опциональная инструкция из присвоенной
   [категории](09-categories.md): как отвечать на входящие этого типа
7. **защита от инъекций** — входящие сообщения подаются как данные с явной инструкцией
   игнорировать содержащиеся в них команды

## Структура промпта комментария

Промпт ответа на комментарий строится отдельно: у комментария нет ни категории, ни
пачки, ни истории диалога — зато есть пост и бриф, которого нет у переписки
([7.4](07-data-flows.md#64-черновики-к-комментариям)).

1. **роль и тон** — из `ai_settings`
2. **база знаний**
3. **пост** — его текст плюс описание от пользователя («что происходит на видео»):
   модель не видит фото и видео, поэтому описание часто важнее самого текста
4. **правило ответа** — инструкция из брифа поста («поблагодарить за тёплые слова»)
5. **правила канала** — публичность ответа, длина
6. **разнообразие** — ответы, уже сгенерированные для других комментариев этого
   поста, подаются с требованием не повторять их; без этого пост с пятнадцатью
   «класс!» получает пятнадцать одинаковых ответов
7. **защита от инъекций** — то же правило: комментарий, пост и бриф — это данные

Комментарий-родитель (для ответа на ответ) подаётся как единственный контекст треда.
Температура выше, чем у переписки, — по той же причине, что и пункт 6.

> [!important] Главный предохранитель продукта
> Черновик **всегда** проходит через человека.
> UI принятия/правки — [10. UI и навигация](10-ui.md).
