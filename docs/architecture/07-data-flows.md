# 7. Потоки данных

> [!info] Навигация
> ⬅️ [6. Модель данных](06-data-model.md) · ⬆️ [Оглавление](_index.md) · ➡️ [8. AI-подсистема](08-ai-subsystem.md)

## 6.1. Входящее (DM или комментарий)

```
Вебхук провайдера
  → /api/webhooks/[provider]
  → проверка подписи
  → адаптер нормализует
  → неразобранные конверты → webhook_events (ключ `unparsed:<ID события>`)
  → запись в webhook_events  (дубль по внешнему ID → сразу 200)
  → одна из трёх веток (ниже)
  → ответ 200
```

Конверт, который адаптер разобрать не смог, тоже попадает в `webhook_events` —
с причиной в `processing_error` и уже проставленным `processed_at` (повтор той
же обработки ничего не изменит). Иначе такая доставка не оставляла бы следа
вообще: роут отвечает 200, провайдер считает её выполненной, а «сообщение
пропало» и «провайдер его не присылал» становятся неразличимы. Ключ
журналируется с префиксом `unparsed:`, чтобы то же событие, доставленное
повторно уже после того, как адаптер научился его читать, не было отброшено как
дубль.

| Событие | Что записывается | Событие Inngest |
|---|---|---|
| `message.received` | contact_identity (+contact и доступный аватар), conversation, message | `push/notify.requested` → мгновенный push; при устаревшем/отсутствующем аватаре — `contact/avatar.sync-requested`. Черновик **не** генерируется |
| `comment.received` | contact_identity (+contact), post (лениво, с описанием и ссылкой из блока `post`), comment | `post/thumbnail.sync-requested` → запрос миниатюры, только если её ещё нет |
| `conversation.started` | conversation (+contact_identity участника) | — |
| `message.sent` | conversation, исходящее message — если оно не наше: сверка по обоим ID сообщения, а для ещё не подтверждённой отправки — привязка к её строке ([5](05-channels.md#нормализованное-событие)) | — |
| `post.published` (у Zernio — `post.external.*` и `post.platform.published`) | post | `post/thumbnail.sync-requested` → первая попытка получить миниатюру |

Комментарий не порождает события генерации: черновик к комментарию создаётся
только по явному запросу пользователя ([6.4](#64-черновики-к-комментариям)).
`post.published` нужен, чтобы только что опубликованный пост появился в
«Публикациях» ещё до первого комментария; для нативно опубликованного поста Zernio
находит его фоновой синхронизацией, поэтому событие приходит с задержкой около часа.
Событие миниатюры содержит только `workspaceId` и `postId`; внешний API вызывается
Inngest-функцией после повторной проверки `posts.thumbnail_url`. Если провайдер ещё
не вернул картинку, поле остаётся пустым, а следующий комментарий естественно
повторяет попытку. Cron и backfill старых постов не используются.

Контакт, созданный под своим внешним ID, получает имя задним числом: как только
провайдер называет участника, `contact_identities.display_name` перезаписывается
всегда (это провайдерская метка), а `contacts.display_name` — только пока там стоит
та самая заглушка, равная внешнему ID. Иначе имя, пришедшее из другого канала после
ручной склейки контактов, затиралось бы первым же WhatsApp-сообщением.

Всё за доли секунды. **LLM в запросе не вызывается никогда.**

> [!danger] Правило
> Вебхук-роуты не вызывают LLM и отвечают < 1 сек; вся тяжёлая работа — события Inngest.
> См. [14. Правила вайбкодинга](14-vibecoding-rules.md).

Адаптер и нормализованное событие — [5. Слой абстракции каналов](05-channels.md).

## 6.2. Генерация черновика

**Черновик к переписке не генерируется сам.** Оператор нажимает значок AI в поле
ответа треда, server action проверяет диалог и эмитит `draft/generate.requested`
(только ID) — этим и живёт функция `generate-draft`. Входящее сообщение само по себе
не запускает ничего.

Так было не всегда: до этого черновик рождался на каждое входящее после окна
дебаунса (`ai_settings.debounce_seconds`), с обратным отсчётом в треде и кнопкой
«Запустить сейчас». Дебаунс отвечал на вопрос «на какую пачку отвечать», но платил
за это токенами по диалогам, которые оператор вести через AI не собирался, — а
собирать пачку умеет и сам пайплайн, без ожидания.

> [!danger] GDPR-правило (жёсткое, в `CLAUDE.md`)
> **Payload любого события Inngest содержит только идентификаторы** —
> `conversationId`, `workspaceId`, `messageId` — и никогда текст сообщений, имена
> или другие персональные данные.
>
> Inngest хранит payload'ы на своей инфраструктуре; при «только ID» через него ходят
> лишь псевдонимные ссылки, а контент функция достаёт из Supabase (Frankfurt)
> в момент выполнения. Это правило ничего не стоит и одновременно является хорошей
> практикой (маленькие события, единый источник истины).
>
> Отражено в таблице субпроцессоров — [15. Compliance](15-compliance-gdpr.md#122-субпроцессоры-и-данные).

### Правила запуска

- Генерация — про переписку. Комментарии идут своим контуром
  ([6.4](#64-черновики-к-комментариям)), и там черновик тоже только по кнопке.
- Черновик отвечает на **пачку** — все входящие после нашего последнего исходящего.
  Если последнее слово было нашим, якорем становится последнее входящее сообщение:
  кнопку жмут и в таком диалоге, и молча отказывать нельзя. В промпт в любом случае
  уходят последние N сообщений.
- Диалог без единого входящего — единственный отказ, и он приходит из самого
  действия, до эмита события: поле ответа блокируется по клику, поэтому прогон,
  который заведомо ничего не создаст, стартовать не должен.
- Новый черновик **вытесняет** прежний (`superseded`), в том числе отредактированный:
  оператор нажал значок и ждёт именно этот текст.
- **Генерацию можно остановить.** Кнопка «стоп» гасит строку черновика
  (`generating` → `discarded`) — именно этот UPDATE разблокирует поле ответа во всех
  открытых вкладках — и шлёт `draft/generate.cancelled`; функция ловит его через
  `cancelOn` по `conversationId`. Отмена срабатывает на границе шагов, поэтому
  начатый вызов LLM доигрывает, но до финализации дело не доходит.
- Прогон, исчерпавший ретраи, помечает свой черновик `failed` (`onFailure`). Это
  UPDATE, а не удаление: поле ответа узнаёт о провале через realtime-подписку на
  `drafts`, а она умеет только INSERT/UPDATE — в payload DELETE нет `workspace_id`,
  по которому фильтруется канал.

### Пайплайн генерации

Шаги Inngest, каждый ретраится независимо:

1. собрать контекст — последние N сообщений диалога, карточка контакта, `ai_settings`,
   [категории базы знаний](09-categories.md), capabilities канала
2. **маскировать идентификаторы** — [8. AI-подсистема](08-ai-subsystem.md#маскирование-идентификаторов-перед-llm);
   в тот же проход собирается фрагмент базы знаний из всех активных категорий
3. **вызвать LLM** — **один** вызов: модель возвращает и черновик, и строку
   `CATEGORIES:` с теми категориями, где нашла факты
   ([контракт](08-ai-subsystem.md#контракт-ответа-categories))
4. обратная подстановка
5. разобрать ответ — отделить строку категорий, развернуть имена в id `kb_files`
6. сохранить draft `ready` — либо, если модель отказалась выдумывать недостающие
   факты, `ready` с пустым текстом и заполненным `manual_review_reason`
   ([8. Заземление](08-ai-subsystem.md#заземление-и-отказ-от-выдумывания)).
   Та же транзакция (`finalize_draft_generation`) пишет категории в
   `drafts.matched_kb_file_ids` и **перезаписывает** `conversations.matched_kb_file_ids`

Готовый текст приезжает в тред через Realtime и подставляется **прямо в поле
ответа** — отдельной панели черновика нет ([10. UI](10-ui.md)).

> [!note] Один вызов LLM вместо двух
> Раньше шагом 3 шла отдельная классификация по категориям на дешёвой модели.
> С тех пор как [категория — это запись базы знаний](09-categories.md), выбирать
> не из чего: в промпт уходят все активные категории, а какие из них пригодились,
> модель сообщает в том же ответе.

Конкурентность ограничена per-workspace (`limit: 2`), чтобы один workspace
не съедал rate limit для всех (см. [17. Риски](17-risks.md)).

## 6.3. Отправка ответа

Пользователь отправил текст из поля ответа (свой или поправленный черновик) →
server action создаёт исходящее message (`sending`)
→ событие `message/send` (**только ID!**) → Inngest-функция шлёт через адаптер
(для комментария — как ответ на конкретный комментарий), обновляет статусы,
при исчерпании ретраев — `failed` и кнопка «повторить» в UI.

Детали реализации (этап 3):

- статус «sending» представлен значением `pending` в `messages.delivery_status`
  (отдельное значение в check-констрейнт не добавлялось); после подтверждения
  провайдера сообщение переходит в `sent`;
- принятие ответа атомарно: RPC `accept_reply_for_send` в одной транзакции
  переводит черновик, из которого взят текст, в `sent`, помечает остальные активные
  черновики диалога `superseded` и вставляет исходящее message `pending`. Текст
  всегда приходит из поля ответа: оператор правит черновик прямо там, и уходить
  должно то, что он видит;
- `messages.external_id` у исходящего заполняется **после** ответа провайдера
  (`providerMessageId`) — именно по нему затем матчатся вебхуки статусов
  `delivered`/`read`/`failed`; до этого поле `null`;
- «повторить» переводит `failed` обратно в `pending` и заново эмитит
  `message/send`.

Для WhatsApp UI заранее предупреждает об истёкшем 24-часовом окне
(по `last_incoming_at` и [capabilities](05-channels.md#capabilities-канала));
отправка при этом не блокируется — отказ провайдера станет `failed` с кнопкой
«повторить».

## 6.4. Черновики к комментариям

Отдельный контур, не пересекающийся с генерацией черновиков переписки.

**Ничего не генерируется само.** Под постом может быть сто комментариев, из
которых половина — «класс!»; решает пользователь, а не пайплайн.

```
Кнопка «Черновики» на посте
  → окно: описание поста + правило ответа (оба необязательны)
  → бриф сохраняется в posts
  → событие comment/drafts.requested (только ID)
  → Inngest generate-comment-drafts:
      для каждого комментария без ответа и без живого черновика,
      последовательно:
        supersede прежнего черновика + insert generating (одна транзакция)
        промпт: текст поста + бриф + сам комментарий
                + уже сгенерированные ответы под этим постом
        LLM → обратная подстановка → draft ready
```

Последовательность и передача уже сгенерированных ответов в промпт — это то, что
не даёт получить пятнадцать одинаковых «Спасибо!». Модель видит, что уже написано
соседям, и обязана ответить иначе.

Отдельные действия пользователя:

- **«Создать черновик»** под комментарием: если бриф поста уже подтверждён —
  генерация запускается сразу, иначе открывается то же окно «Черновики»;
- **кнопка обновления** у черновика — та же функция для одного комментария:
  прежний черновик становится `superseded`, генерируется новый;
- **«Отклонить»** — черновик уходит в `discarded` и в отправку не попадает;
- **«Отправить все»** — все `ready`/`edited` черновики поста отправляются по
  очереди; каждый — своей транзакцией `accept_comment_draft_for_send` и своим
  событием `comment/send`.

Ответ всегда публикуется под тем комментарием, на который отвечает:
`comments.parent_external_id` исходящего заполняется в той же транзакции, что и
перевод черновика в `sent`.

## 6.5. Email (этап после MVP)

**Postmark Inbound:** каждому workspace — адрес `w-{id}@inbound.домен` + инструкция
по переадресации с реального ящика. Postmark парсит MIME сам и присылает JSON-вебхук —
`postmarkAdapter` превращает его в то же нормализованное событие.

**Тредирование:** `In-Reply-To` / `References` с фолбэком «контакт + нормализованный subject».

**Исходящие** — тоже Postmark, с корректными заголовками треда и `Reply-To` на inbound-адрес;
SPF/DKIM/DMARC к этому моменту уже настроены (они нужны с этапа auth-писем —
см. [4. Приглашения](04-multitenancy.md#приглашения)).

> [!tip] Email — не отдельная подсистема
> Это `kind = dm` с email-capabilities. Вся заслуга — у
> [слоя абстракции каналов](05-channels.md).
> Этап — [Этап 11](16-rollout-plan.md#этап-11-после-запуска--email-канал-2-3-дня).

## 6.6. Полный список Inngest-функций

| Функция | Назначение |
|---|---|
| `generate-draft` | пайплайн генерации по запросу оператора: один вызов LLM, [категории](09-categories.md) приходят его же ответом; отменяется через `cancelOn` |
| `regenerate-draft` | перегенерация черновика переписки по запросу пользователя |
| `generate-comment-drafts` | черновики к комментариям поста — по запросу пользователя ([6.4](#64-черновики-к-комментариям)) |
| `send-message` | исходящие через адаптер |
| `send-comment` | публикация ответа на конкретный комментарий |
| `send-comment-private-reply` | личное сообщение автору комментария (Meta private reply); отказ платформы (окно 7 дней, повтор) приходит как 4xx и ретраям не подлежит |
| `send-push` | Web Push на каждое входящее — для пользователей в режиме «каждое входящее» ([11. PWA](11-realtime-pwa.md#web-push)); событие эмитит вебхук-пайплайн сразу после записи сообщения |
| `contact-avatar` | фоновая загрузка фото одного участника через API адаптера; событие содержит только IDs |
| `post-thumbnail` | получает миниатюру одного поста через API адаптера; повторные события ничего не делают после заполнения `thumbnail_url` |
| `push-digest` | cron: сводки для пользователей в режиме «дайджест» — счётчики и список новых входящих с прошлой сводки, по интервалу из [`notification_settings`](06-data-model.md#notification_settings) |
| `reconcile-webhooks` | cron: переобработать зависшие `webhook_events` — страховка |
| `cleanup` | cron: старые `webhook_events` по политике ретенции, мёртвые push-подписки |
| `cleanup-ai-request-log` | cron (ночью): удаляет записи [`ai_request_log`](06-data-model.md#ai_request_log) старше 30 дней — ретенция журнала промптов и ответов |
| `notify-existing-user` *(позже)* | письмо-приглашение уже зарегистрированному пользователю через Postmark API — см. [4. Мультитенантность](04-multitenancy.md#краевой-случай-приглашённый-уже-зарегистрирован) |

> [!note] Заметьте
> Функции отправки инвайтов **новым** пользователям нет — эти письма шлёт Supabase Auth
> через Postmark-SMTP.
