# 7. Потоки данных

> [!info] Навигация
> ⬅️ [6. Модель данных](06-data-model.md) · ⬆️ [Оглавление](_index.md) · ➡️ [8. AI-подсистема](08-ai-subsystem.md)

## 6.1. Входящее (DM или комментарий)

```
Вебхук провайдера
  → /api/webhooks/[provider]
  → проверка подписи
  → запись в webhook_events  (дубль по внешнему ID → сразу 200)
  → адаптер нормализует
  → upsert contact_identity (+contact), conversation
  → insert message
  → inngest.send("interaction/received")
  → ответ 200
```

Всё за доли секунды. **LLM в запросе не вызывается никогда.**

> [!danger] Правило
> Вебхук-роуты не вызывают LLM и отвечают < 1 сек; вся тяжёлая работа — события Inngest.
> См. [14. Правила вайбкодинга](14-vibecoding-rules.md).

Адаптер и нормализованное событие — [5. Слой абстракции каналов](05-channels.md).

## 6.2. Дебаунс и генерация черновика

Здесь Inngest окупается полностью: у него есть **нативный debounce**.

Функция `generate-draft` подписана на `interaction/received` с конфигурацией debounce
по ключу `conversationId` и периодом из настроек workspace (`ai_settings.debounce_seconds` —
[6. Модель данных](06-data-model.md#ai_settings)). Семантика ровно та, что нужна:
каждое новое сообщение в диалоге перезапускает таймер, и функция выполняется один раз
после паузы — с данными последнего события. Никаких самодельных таймеров, cron-проверок и гонок.

> [!danger] GDPR-правило (жёсткое, в `CLAUDE.md`)
> **Payload любого события Inngest содержит только идентификаторы** — `messageId`,
> `conversationId`, `workspaceId` — и никогда текст сообщений, имена или другие
> персональные данные.
>
> Inngest хранит payload'ы на своей инфраструктуре; при «только ID» через него ходят
> лишь псевдонимные ссылки, а контент функция достаёт из Supabase (Frankfurt)
> в момент выполнения. Это правило ничего не стоит и одновременно является хорошей
> практикой (маленькие события, единый источник истины).
>
> Отражено в таблице субпроцессоров — [15. Compliance](15-compliance-gdpr.md#122-субпроцессоры-и-данные).

### Правила поверх дебаунса

- Для `kind = comments` и для email дебаунс не нужен (или минимальный) — комментарий
  и письмо самодостаточны; классификация по категориям для них выполняется поштучно.
- Период — настройка per-workspace.
- Если к моменту генерации в диалоге уже есть черновик со статусом `ready`,
  он помечается `superseded`, генерируется новый по полному контексту
  (пользователь не должен увидеть два конкурирующих черновика).

### Пайплайн генерации

Шаги Inngest, каждый ретраится независимо:

1. собрать контекст — последние N сообщений диалога, карточка контакта, `ai_settings`,
   применимые [категории](09-categories.md), capabilities канала,
   для комментариев — текст поста
2. **маскировать идентификаторы** — [8. AI-подсистема](08-ai-subsystem.md#маскирование-идентификаторов-перед-llm);
   выполняется до классификации, потому что она тоже ходит в LLM
3. **классифицировать по категориям** — один LLM-вызов на пачку
   ([промпт](08-ai-subsystem.md#классификация-по-категориям)): из категорий workspace
   отбираются применимые к каналу и типу входящего, проверка идёт по приоритету,
   первая подходящая (или «по умолчанию») записывается в `category_id`
   **всех сообщений пачки**
4. **стоп-проверка** — если у категории флаг «не создавать черновиков» или
   авто-генерация выключена в `ai_settings`, пайплайн завершается
   (классификация уже сохранена)
5. подобрать файлы базы знаний
6. вызвать LLM — в промпт добавляется «действие» присвоенной категории
7. обратная подстановка
8. сохранить draft `ready`
9. событие для push-уведомления — доставка зависит от режима пользователя
   ([11. Частота уведомлений](11-realtime-pwa.md#частота-уведомлений--настройка-пользователя))

> [!note] Классификация выполняется всегда
> Даже когда черновик не создаётся (флаг категории, выключенная авто-генерация),
> шаги 1–4 выполняются: каждое входящее должно получить категорию.

Конкурентность ограничена per-workspace (`limit: 2`), чтобы один workspace
не съедал rate limit для всех (см. [17. Риски](17-risks.md)).

## 6.3. Отправка ответа

Пользователь принял/поправил черновик → server action создаёт исходящее message (`sending`)
→ событие `message/send` (**только ID!**) → Inngest-функция шлёт через адаптер
(для комментария — как ответ на конкретный комментарий), обновляет статусы,
при исчерпании ретраев — `failed` и кнопка «повторить» в UI.

Для WhatsApp UI заранее предупреждает об истёкшем 24-часовом окне
(по `last_incoming_at` и [capabilities](05-channels.md#capabilities-канала)).

## 6.4. Email (этап после MVP)

**Postmark Inbound:** каждому workspace — адрес `w-{id}@inbound.домен` + инструкция
по переадресации с реального ящика. Postmark парсит MIME сам и присылает JSON-вебхук —
`postmarkAdapter` превращает его в то же нормализованное событие.

**Тредирование:** `In-Reply-To` / `References` с фолбэком «контакт + нормализованный subject».

**Исходящие** — тоже Postmark, с корректными заголовками треда и `Reply-To` на inbound-адрес;
SPF/DKIM/DMARC к этому моменту уже настроены (они нужны с этапа auth-писем —
см. [4. Приглашения](04-multitenancy.md#приглашения)).

> [!tip] Email — не отдельная подсистема
> Это `kind = dm` с email-capabilities. Вся заслуга — у
> [слоя абстракции каналов](05-channels.md).
> Этап — [Этап 11](16-rollout-plan.md#этап-11-после-запуска--email-канал-2-3-дня).

## 6.5. Полный список Inngest-функций

| Функция | Назначение |
|---|---|
| `generate-draft` | debounce, классификация по [категориям](09-categories.md), пайплайн генерации |
| `send-message` | исходящие через адаптер |
| `send-push` | Web Push на каждое входящее — для пользователей в режиме «каждое входящее» ([11. PWA](11-realtime-pwa.md#web-push)) |
| `push-digest` | cron: сводки для пользователей в режиме «дайджест» — счётчики и список новых входящих с прошлой сводки, по интервалу из [`notification_settings`](06-data-model.md#notification_settings) |
| `reconcile-webhooks` | cron: переобработать зависшие `webhook_events` — страховка |
| `cleanup` | cron: старые `webhook_events` по политике ретенции, мёртвые push-подписки |
| `notify-existing-user` *(позже)* | письмо-приглашение уже зарегистрированному пользователю через Postmark API — см. [4. Мультитенантность](04-multitenancy.md#краевой-случай-приглашённый-уже-зарегистрирован) |

> [!note] Заметьте
> Функции отправки инвайтов **новым** пользователям нет — эти письма шлёт Supabase Auth
> через Postmark-SMTP.
