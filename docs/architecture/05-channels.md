# 5. Слой абстракции каналов

> [!info] Навигация
> ⬅️ [4. Мультитенантность](04-multitenancy.md) · ⬆️ [Оглавление](_index.md) · ➡️ [6. Модель данных](06-data-model.md)

Ключевое решение прежнее: весь провайдер-специфичный код изолирован в адаптерах
(`lib/channels/*` — см. [12. Структура репозитория](12-repo-structure.md)),
ядро оперирует только нормализованными событиями.

Это делает будущий переход с Zernio на прямой Meta App заменой одного модуля,
а email — просто третьим адаптером
(см. [6.4. Email](07-data-flows.md#64-email-этап-после-mvp)).

## Один канал каждой платформы и имена

Workspace может подключить **не больше одного канала каждой платформы**. Ограничение
закреплено уникальностью `(workspace_id, platform)` в БД и повторено в UI/server action,
чтобы не начинать заведомо лишний OAuth-флоу. У подключения есть **имя** — поле `name`
в [`channel_connections`](06-data-model.md#channel_connections). Пользователь его **не
вводит**: имя подставляется из имени подключённого аккаунта (провайдер возвращает его в
callback), а переименовать канал можно в любой момент в настройках.

Имя протекает в продукт:

- в списках сообщений/комментариев и в треде виден именованный канал-источник
  ([10. UI](10-ui.md#откуда-пришло-входящее));
- в меню каналы перечисляются под своими именами со счётчиками новых входящих;

Управление подключениями (добавить, переименовать, отключить, удалить) — раздел «Каналы»
в настройках ([10. Разделы настроек](10-ui.md#разделы-настроек)). Раздел разбит на
блоки по платформам (Instagram, Telegram, WhatsApp, Facebook, Email), разделённые
горизонтальной чертой: пока платформа не подключена, блок — это кнопка
«Подключить <канал>» со значком мессенджера; подключённая платформа показывает строку
своего канала. «Подключить» — это OAuth-подключение (см.
[Подключение аккаунта](#подключение-аккаунта-oauth)): пользователь авторизует аккаунт
соцсети, не открывая дашборд провайдера. Платформы, для которых флоу ещё не готов,
показывают заглушку «в разработке» (на старте работает только Instagram; у Email пока
нет и адаптера).

### Отключить ≠ удалить

Это два разных действия над подключением:

- **«Отключить»** меняет `status` на `disconnected`. Переписка остаётся, новые входящие
  просто не обрабатываются; включить обратно — одна кнопка.
- **«Удалить»** (иконка корзины, с подтверждением) стирает строку
  [`channel_connections`](06-data-model.md#channel_connections). Каскадом уходят диалоги,
  посты, сообщения и комментарии этого канала.
  Перед удалением строки аккаунт отключается у провайдера (`disconnectAccount`); **в самой
  соцсети ничего не удаляется** — сообщения и комментарии остаются там.

## Интерфейс адаптера

Концептуально:

1. проверить подпись вебхука
2. распарсить сырой payload в нормализованные события
3. отправить исходящее
4. дать ссылку авторизации для подключения аккаунта соцсети (`getConnectUrl`)
5. разобрать callback провайдера во внешний ID подключённого аккаунта
   (`parseConnectCallback`)
6. отключить аккаунт у провайдера при удалении канала (`disconnectAccount`)
7. получить фото конкретного участника (`fetchParticipantAvatar`)
8. получить миниатюру конкретного поста (`fetchPostThumbnail`)

## Подключение аккаунта (OAuth)

Подключение канала — самостоятельный OAuth-флоу внутри drafta. **Пользователь не
имеет доступа к дашборду провайдера (Zernio) и не вводит внешний ID вручную:**

1. в разделе «Каналы» пользователь жмёт «Подключить <канал>»; вместо кнопки
   раскрывается онбординг с предусловиями (для Instagram — профессиональный аккаунт
   Business/Creator и вход именно в нужный аккаунт в этом же браузере, чтобы на
   следующем шаге не подключить чужой) и кнопкой «Войти через <канал>»;
2. сервер читает обязательный **профиль провайдера** workspace (у Zernio аккаунты
   группируются в «профиль»; отдельный профиль уже создан при bootstrap workspace), затем через
   `getConnectUrl` адаптера — серверный вызов Zernio REST
   `GET /v1/connect/{platform}` (Bearer `ZERNIO_API_KEY`) — получает `authUrl`;
3. браузер уходит на `authUrl`; провайдер проводит OAuth платформы и редиректит на наш
   callback-роут `app/api/channels/[provider]/connect/callback/`, дописывая
   `connected` (платформа), `accountId`, `username`;
4. роут проверяет подписанный `state` и создаёт
   [`channel_connections`](06-data-model.md#channel_connections) с `external_id = accountId`
   и `name` из `username` (если провайдер его не прислал — из названия платформы).

Обратная операция — при удалении канала drafta зовёт `disconnectAccount` адаптера; у
Zernio это `DELETE /v1/accounts/{accountId}` (`deleteAccount` в их OpenAPI: «Disconnects
and removes a connected social account»), то есть один вызов и отключает, и удаляет
подключение на стороне провайдера. 404 считается успехом — аккаунта у провайдера уже
нет. Если вызов не удался, канал в drafta всё равно удаляется, а пользователь получает
предупреждение: доступ стоит отозвать в самой соцсети.

Провайдер-специфика (вызовы Zernio API, разбор callback) живёт только в
`lib/channels/zernio/` (`api.ts`, `connect.ts` — см. [Дисциплина](#дисциплина)). Внешний
ID (`accountId`) из callback совпадает с тем, что провайдер присылает во входящих
вебхуках, — поэтому связка `(провайдер, внешний ID)` резолвит то же подключение
([6.1. Входящее](07-data-flows.md#61-входящее-dm-или-комментарий)).

> [!note] Защита от CSRF без round-trip провайдера
> Zernio не возвращает наш произвольный `state` в callback. Поэтому подписанный
> `state` (workspace, платформа, nonce) кладётся в httpOnly-cookie, а его `nonce`
> эхом добавляется в `redirect_url` (`?cn=…`); callback читает `state` из cookie и
> сверяет `cn` с его `nonce` (double-submit).

> [!note] Профиль провайдера и токены
> ID профиля Zernio для workspace хранится в
> [`workspaces.settings.providerProfiles.<провайдер>`](06-data-model.md#workspaces).
> Токены платформ держит сам Zernio — drafta сохраняет только внешний ID
> (`channel_connections.encrypted_credentials` пусто). Прямой Meta App в будущем будет
> складывать сюда собственные токены ([16. За горизонтом](16-rollout-plan.md)).

### Создание workspace и Zernio Profile

Zernio Profile — обязательная внешняя граница тенанта, соответствующая workspace 1:1.
Workspace не создаётся без Profile:

1. server action проверяет Supabase-сессию и генерирует UUID будущего workspace;
2. создаёт Zernio Profile с уникальным техническим именем `drafta-<workspace UUID>`;
3. server-only RPC одной транзакцией создаёт `workspaces`, owner membership и
   `ai_settings`, сразу записывая `settings.providerProfiles.zernio`;
4. если транзакция БД не состоялась, пустой Zernio Profile удаляется компенсацией.

RPC доступен только `service_role`: браузер не может обойти provisioning прямым вызовом.
Если Zernio недоступен, onboarding завершается ошибкой до появления workspace в БД.
Миграция/ленивое создание профилей для старых workspace не предусмотрены: на момент
введения инварианта пользовательских данных в БД нет.

## Нормализованное событие

Это не одна форма, а **три разных**, различаемых по типу события — переписка,
комментарий и публикация поста живут в разных таблицах и разных пайплайнах, так что
общая форма с полем-дискриминатором заставляла бы ветвиться каждого потребителя.

Общее у всех трёх:

- **ID события у провайдера** — для идемпотентности
  (см. [6.1. Входящее](07-data-flows.md#61-входящее-dm-или-комментарий))
- **провайдер**, **платформа**, **внешний ID подключённого аккаунта**
- **«сырые» метаданные провайдера**, которые нельзя терять: email-заголовки,
  ID поста и родительского комментария и т.п.

| Тип | Специфичные поля |
|---|---|
| `message.received`, `message.delivered/read/failed` | ссылка на диалог + сообщение (текст, вложения, отправитель) |
| `comment.received` | ссылка на пост (внешний ID, описание, ссылка, миниатюра) + комментарий (текст, автор, ID родительского комментария) |
| `post.published` | только пост: внешний ID, описание, ссылка, миниатюра, время публикации |

Отправитель сообщения и автор комментария используют одну нормализованную форму:
внешний ID, имя и необязательную ссылку на фото профиля. Для Zernio у DM в первую
очередь берётся `conversation.participantPicture`, резервно —
`message.sender.picture`; у комментария — `comment.author.picture`. Если webhook
фото не содержит, после сохранения входящего отправляется IDs-only событие
`contact/avatar.sync-requested`, а Inngest читает картинку через API адаптера.
Внешние запросы из webhook-роута не выполняются.

В карточке выбранного контакта пользователь может вручную запросить актуальное
фото кнопкой на аватаре. Сервер последовательно проверяет identities контакта в
порядке Instagram → Facebook → Telegram → WhatsApp → остальные платформы и
останавливается на первом найденном фото. Это явное пользовательское действие;
периодического обхода всех контактов нет.

`post.published` — то, благодаря чему только что опубликованный пост появляется в
«Публикациях» до первого комментария. У Zernio под этим нормализованным типом
объединены два разных вебхука:

- `post.external.created` / `post.external.updated` — пост, опубликованный
  **нативно** (из приложения Instagram, а не через Zernio). Это обычный случай для
  наших пользователей. Zernio находит такие посты фоновой синхронизацией, поэтому
  событие приходит с задержкой около часа, а не в реальном времени;
- `post.platform.published` — пост, опубликованный **через Zernio**: одно событие на
  каждую платформу, с `account.accountId` и `platform.platformPostId`.

Постовый rollup `post.published` у Zernio намеренно не обрабатывается: в его payload
нет подключённого аккаунта (аккаунты лежат внутри `post.platforms[]`), а каждая его
цель и так приходит отдельным `post.platform.published`.

Описание, ссылку и миниатюру поста приносит и вебхук комментария: блок `post` в
`comment.received` несёт `content`, `permalink` и `imageUrl` из синхронизированной
копии поста у Zernio. Строка `posts` при этом только **дополняется** — заполняются
пустые колонки, уже сохранённое не затирается.

Миниатюра поста дополнительно обогащается отдельно от webhook-пути: после каждого из
этих событий отправляется IDs-only событие `post/thumbnail.sync-requested`. Inngest
сначала проверяет сохранённый `posts.thumbnail_url` и вызывает `fetchPostThumbnail`
только пока он пуст — то есть после вебхука с картинкой это обычный no-op. Для Zernio
адаптер читает поле `picture` из `GET /v1/inbox/comments`; старые посты без новой
активности не обходятся и периодического backfill нет.

## Capabilities канала

Свойства, которые честно протекают в продукт и **хранятся как данные, а не зашиты в код**:

| Capability | Пример различий |
|---|---|
| Окно ответа | WhatsApp — 24 часа; email — нет |
| Поддержка вложений | зависит от платформы |
| Статусы прочтения | есть/нет |
| Лимит длины | зависит от платформы |
| Стиль тредирования | плоский / по родителю / по заголовкам письма |
| Поддержка комментариев | есть/нет |

UI и AI-промпт читают capabilities: черновик для Instagram-комментария — короткий и публичный,
для email — с приветствием и подписью
(см. [8. Структура промпта](08-ai-subsystem.md#структура-промпта)).

Хранятся в `channel_connections.capabilities` (jsonb) —
[6. Модель данных](06-data-model.md#channel_connections).

## Дисциплина

> [!danger] Правило для AI-агента, фиксируется в `CLAUDE.md`
> Ни один файл вне `lib/channels/` не импортирует SDK и типы Zernio / Postmark / Meta.
> Точка отправки — только через адаптер.
> См. [14. Правила вайбкодинга](14-vibecoding-rules.md).

Контракт абстракции проверяется юнит-тестами на адаптеры: фикстуры реальных payload'ов
→ ожидаемые нормализованные события. Фикстуры накапливаются сами — они уже лежат
в `webhook_events`.
