# Vercel Workflow основного приложения

Реализация: `lib/workflows/`; бизнес-код: `lib/jobs/`. SDK закреплён на
`workflow@5.0.0-beta.53`: эта версия поддерживает совместное размещение
исполнения и состояния в регионе запуска. Все `start()` используют `fra1` и
`experimental_retention: 0` — содержимое завершённых runs/steps удаляется,
метаданные остаются по политике Vercel. Фактическое облачное размещение проверяется
на тестовом deployment; локальная сборка его не подтверждает.

| Прежняя функция | Workflow | Назначение |
|---|---|---|
| generate-draft | generateDraftWorkflow | Черновик ответа в переписке |
| auto-reply | autoReplyWorkflow | Ожидание, классификация, постановка шаблонного ответа на отправку |
| send-message | sendMessageWorkflow | Отправка сообщения |
| send-comment | sendCommentWorkflow | Публичный ответ на комментарий |
| send-comment-private-reply | sendCommentPrivateReplyWorkflow | ЛС автору комментария |
| send-push | sendPushWorkflow | Push отдельно каждому устройству |
| contact-avatar | syncContactAvatarWorkflow | Обновление фото контакта |
| post-thumbnail | syncPostThumbnailWorkflow | Загрузка миниатюры поста |
| publication-generation | generatePublicationWorkflow | Текст, идеи и изображения публикации |
| publication-import | importPublicationWorkflow | Импорт файлов из GPT |
| publication-send | publishPublicationWorkflow | Публикация или проверка результата отправки |
| cleanup-ai-request-log | cleanupAiRequestLogWorkflow | Удаление AI-логов старше 30 дней |
| cleanup-publication-assets | cleanupPublicationAssetsWorkflow | Удаление сирот и устаревших служебных записей, сверка остановившихся операций |

`generate-comment-drafts` удалён; исторические таблицы не удаляются. `website/`
с отдельным Inngest-приложением не входит в миграцию.

## Повторы и доставка

Бизнес-steps пользовательских операций имеют `maxRetries=0`. Ошибка видна в
переписке, комментариях либо редакторе публикации; повтор запускает пользователь.
Push и две очистки имеют максимум два дополнительных повтора. Служебная запись
итогового состояния допускает два повтора БД и не повторяет бизнес-действие.

`workflow_operations` имеет RLS, каскад от workspace, уникальный ключ по
workspace/kind/subject, отдельный `attempt_id` и владельца `run_id`.
RPC резервирования и захвата сериализуют двойной клик и ограничивают исполнение:
две обычные операции и четыре push на workspace, одна операция на ресурс.
Отмена закрывает попытку перед вызовом SDK; последующие этапы проверяют её ID.
Зависшие записи сверяются с состоянием SDK при открытии треда и почасовой очистке.
Недоступность API состояния не считается доказательством остановки.

До внешней отправки сообщения записывается маркер эффекта. Потеря ответа
провайдера означает `uncertain`: автоматическая отправка запрещена, UI требует
проверить исходный канал. При сохранённом ID результата повтор завершает запись
статуса без повторной отправки. Публикации с `first_sent_at` без известного
результата только сверяются; «Проверить статус» не вызывает publish/retry.
Повтор подтверждённого отказа публикации использует прежний remote ID.

Журнал автоответа содержит `queued` до подтверждения отправки сообщения;
триггеры БД переводят его в `sent`. Сбой автоответа можно повторить в переписке.
Созданное исходящее сообщение используется повторно, если сбой произошёл после
его создания. Генерация публикаций сохраняет завершённые этапы, импорт — ID
успешных файлов. Просроченные ссылки импорта требуют свежих файлов.

В аргументах и результатах durable steps — ID, статусы и дедлайны. Тексты,
промпты, токены, push endpoints, подписанные URL и файлы читаются из Supabase
внутри steps и не возвращаются в Workflow. Ошибки бизнес-шага заменяются
безопасным кодом без исходного сообщения провайдера.

## Локальный запуск и проверки

Применить миграции к изолированной Supabase, затем `pnpm dev`. Отдельный сервер
очереди не требуется. `pnpm exec workflow inspect` открывает инструменты
наблюдения SDK. Сгенерированные `app/.well-known/workflow/` доступны без
пользовательской сессии и не проходят через auth proxy; их транспорт защищает SDK.

```powershell
pnpm test
pnpm exec tsc --noEmit
pnpm lint
pnpm build
```

`lib/workflows/operations.test.ts` исполняет настоящую SQL-миграцию в изолированном
PostgreSQL PGlite: RLS, права, дедупликация, лимиты, fencing, журнал автоответов.
Это не заменяет полный `pnpm test:rls` и `pnpm exec supabase test db` на
разрешённой Supabase с полной схемой. Не направлять тесты на production.

## Production: переключение

1. Применить `20260919100000_workflow_operations.sql` сначала к dev, проверить
   полный SQL/RLS-контур. Миграция добавочная; старый код ещё может работать.
2. Проверить тестовый Vercel deployment: 13 Workflow, запуск и отмена, регион fra1,
   ID-only данные, удаление payload после завершения, длительность тяжёлого шага.
   Почасовой Cron требует подходящего тарифа. Проверить предел длительности
   функций проекта для импорта и генерации изображений.
3. Установить длинный случайный `CRON_SECRET`. `vercel.json` задаёт UTC:
   `/api/cron/ai-request-log` — `0 3 * * *`,
   `/api/cron/publication-assets` — `17 * * * *`.
   Запрос без Bearer-секрета получает 401. Cron стартует workflow и возвращает 202.
4. На короткое окно остановить новые фоновые действия старого deployment.
   Дождаться завершения старых Inngest runs либо отменить и сверить их вручную,
   включая спящие автоответы. Проверить pending/uncertain отправки в исходных
   каналах. Не передавать одну операцию двум движкам одновременно.
5. Переключить deployment. Проверить входящее → черновик → отправку, искусственный
   отказ → ручной повтор; комментарий/ЛС, автоответ/отмену, публикации, push и Cron.
   Отключить Inngest-интеграцию и удалить INNGEST_* только у основного приложения.
6. Настроить наблюдение за failed Cron runs в Vercel и ошибками/старыми активными
   записями `workflow_operations` в Supabase. Ошибки бизнес-действий отражаются
   в этой таблице даже когда управляющий workflow успешно сохранил ошибку.

Rollback: остановить новые запуски, отменить/сверить Workflow, затем вернуть
предыдущий deployment. Не удалять добавочные таблицы/статусы и не включать оба
движка для одних отправок. Неизвестную доставку сначала проверить вручную.
