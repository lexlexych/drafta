# T-08. Executive summary — ручные шаги

> Этот тикет выполняет **человек** после завершения всех dev-тикетов эпика.
> Агенты сюда только дописывают шаги. Формат шага: зачем → что сделать → как проверить.

## Предусловия

- Dev-тикеты T-01–T-07 в статусе `done`.
- Аккаунты (или готовность их создать): Supabase, Vercel, Postmark, GitHub (или другой git-хостинг).
- Домен во владении — для auth-писем Postmark (открытый вопрос №1 эпика: какой именно).
- Доступ к DNS-настройкам домена.

## Шаги

### 1. Создать два проекта Supabase — prod и dev — в регионе Frankfurt

- **Зачем:** регион задаётся при создании и потом трудно меняется; Frankfurt — GDPR-решение
  первого дня ([3. Стек](../../architecture/03-stack.md#решения-первого-дня)).
- **Что сделать:** в дашборде Supabase создать проекты `drafta-prod` и `drafta-dev`,
  регион **Frankfurt (eu-central-1)** у обоих. Сохранить для каждого: Project URL,
  `sb_publishable_…` и `sb_secret_…` ключи (Settings → API Keys).
- **Проверка:** в Settings → General у обоих проектов указан регион Frankfurt.

### 2. Применить миграции и включить подтверждение email

- **Зачем:** схема v1 из репозитория должна попасть в облачные проекты — только через
  миграции, не через дашборд (правило 2).
- **Что сделать:** локально `supabase link --project-ref <ref>` и `supabase db push` —
  сначала на dev, затем на prod. В Authentication → Sign In / Providers включить Email
  и убедиться, что «Confirm email» включён.
- **Проверка:** в Table Editor обоих проектов видны все 15 таблиц; в каждой включён RLS.

### 2a. Подтвердить RLS-изоляцию в Supabase Cloud dev

- **Зачем:** локальная runtime-проверка не выполнялась, потому что на машине запрещено
  использовать Docker. После `supabase db push` нужно проверить, что PostgreSQL принял
  миграции T-03 и реально применяет политики к запросам с publishable-ключом.
- **Что сделать:** только на тестовых пользователях и тестовых данных выполнить SQL-сценарий
  в dev-проекте. Подготовить два независимых workspace (A и B) и отдельного пользователя с
  ролью `member` в одном из них. В транзакции эмулировать JWT сессии через `set local role
  authenticated` и `set_config('request.jwt.claim.sub', '<user-id>', true)` (при необходимости
  также заполнить `request.jwt.claims` с `sub` и `role: authenticated`). Проверить: пользователь
  A не получает строки workspace B; INSERT/UPDATE/DELETE строки с `workspace_id` B получают
  RLS-ошибку; SELECT `workspace_members` своего workspace возвращает участников без ошибки
  рекурсии; пользователь с ролью `member` не может менять workspace, участников или invitations;
  `webhook_events` не читается клиентской ролью; роль `anon` получает ноль строк либо отказ в
  доступе. Откатить транзакцию либо удалить тестовые данные после проверки.
- **Проверка:** все отрицательные запросы завершились нулём строк или ожидаемой RLS/permission
  ошибкой, разрешённые запросы участника видят только его workspace. Результат сценария
  зафиксирован в отчёте T-03 и повторён ревьюером.

### 3. Создать удалённый git-репозиторий и подключить Vercel (регион fra1)

- **Зачем:** деплой через `git push`; регион функций fra1 — GDPR-решение первого дня.
- **Что сделать:** создать приватный репозиторий (например, GitHub `drafta`), запушить
  `main` (push агенты сами не делают — попросить или сделать самому). В Vercel — New
  Project из этого репозитория; в настройках проекта выставить Function Region **fra1
  (Frankfurt)**. В Environment Variables прописать: `NEXT_PUBLIC_SUPABASE_URL`,
  `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY` — значения prod-проекта
  для Production (dev-проекта — для Preview, по желанию). Значения секретов нигде не
  коммитить.
- **Проверка:** прод-деплой открывается по URL Vercel, страница входа отображается.

### 4. Postmark: аккаунт, домен, DKIM/SPF

- **Зачем:** встроенная почта Supabase в проде фактически не работает (лимит 2 письма/час
  только участникам проекта) — без Postmark нет регистрации и сброса пароля
  ([3. Стек](../../architecture/03-stack.md)); домен и DKIM переиспользуются этапом 11.
- **Что сделать:** создать аккаунт Postmark, добавить Sender Signature / Domain
  (выбранный домен), в DNS домена добавить записи DKIM и Return-Path (SPF), которые
  покажет Postmark. Дождаться верификации. Взять SMTP-креды сервера
  (Message Stream: transactional).
- **Проверка:** домен в Postmark в статусе Verified (DKIM и Return-Path зелёные).

### 5. Подключить Postmark как custom SMTP в Supabase Auth (prod)

- **Зачем:** чтобы auth-письма (регистрация, сброс пароля, будущие инвайты) уходили
  через Postmark ([13. Разовая настройка](../../architecture/13-environments-secrets.md#разовая-ручная-настройка-не-код)).
  SMTP-креды живут в дашборде Supabase, не в env приложения.
- **Что сделать:** prod-проект → Authentication → Emails → SMTP Settings: включить Custom
  SMTP, host/port/логин/пароль из Postmark, Sender email — адрес на верифицированном
  домене (например, `no-reply@<домен>`), Sender name — `drafta`.
- **Проверка:** тестовая регистрация на прод-домене — письмо подтверждения приходит на
  реальный ящик; в Postmark Activity видна отправка.

### 6. Поднять лимиты auth-писем (Rate Limits)

- **Зачем:** дефолтный лимит писем в час слишком мал под реальный поток регистраций
  ([13](../../architecture/13-environments-secrets.md#разовая-ручная-настройка-не-код)).
- **Что сделать:** prod-проект → Authentication → Rate Limits → «Rate limit for sending
  emails» — поднять до разумного значения (например, 100/час; доступно после включения
  custom SMTP).
- **Проверка:** значение сохранено и отображается в настройках.

### 7. Настроить Auth URLs (prod)

- **Зачем:** ссылки в письмах должны вести на прод-домен, а не на localhost.
- **Что сделать:** prod-проект → Authentication → URL Configuration: Site URL —
  прод-URL Vercel; в Redirect URLs добавить пути подтверждения/сброса из T-04
  (и preview-домены Vercel при необходимости).
- **Проверка:** ссылка из письма подтверждения открывает прод-домен и завершает вход.

### 8. Запросить DPA у Zernio (параллельно, вход в этап 1)

- **Зачем:** подписанный DPA Zernio — входное условие этапа 1; переписка занимает время,
  начать сейчас ([15.2](../../architecture/15-compliance-gdpr.md#122-субпроцессоры-и-данные)).
- **Что сделать:** через Trust Center Zernio (trust.zernio.com, под NDA) запросить DPA
  и задать вопросы из §15.2: их список субпроцессоров (в Trust Center пусто — явно
  неполно), локация обработки и наличие SCC/DPF, ретенция контента сообщений у них.
- **Проверка:** DPA получен на подпись; ответы на вопросы §15.2 зафиксированы
  (в переписке/заметках) — итог отражён в решении о старте этапа 1.

## Финальная проверка эпика

Критерий этапа 0 из [плана внедрения](../../architecture/16-rollout-plan.md#этап-0--фундамент-1-2-дня):

1. На прод-URL зарегистрировать пользователя с **реальным email** — письмо приходит
   (через Postmark), подтверждение проходит, онбординг создаёт workspace A.
2. Во втором браузере/профиле зарегистрировать второго пользователя с другим реальным
   email — workspace B.
3. Убедиться: каждый видит в dashboard только свой workspace; данные друг друга
   недоступны. Локально это же подтверждает `npm run test:rls` (T-06).
