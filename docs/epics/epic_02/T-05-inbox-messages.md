# T-05. Инбокс «Сообщения»: список диалогов и тред

## Цель

Экран «Сообщения» работает: список диалогов `kind = dm` со всех каналов workspace
(имя контакта, превью последнего сообщения, **бейдж имени канала-источника**,
счётчик непрочитанного), открытие треда с историей сообщений, фильтр по каналу;
в меню — пункт «Сообщения» со счётчиком и расхлопом по каналам под их именами.

## Контекст

Обязательно прочитать перед выполнением:

- [10. UI и навигация](../../architecture/10-ui.md) — **вся глава**: десктопное левое
  меню, мобильная нижняя панель, «Откуда пришло входящее», «Экраны инбокса»
- [1. Что мы строим, «Два ящика»](../../architecture/01-overview.md) — механика инбоксов
- [6. Модель данных](../../architecture/06-data-model.md) — `conversations` (статус, `last_incoming_at`, счётчик непрочитанного), `messages`, `contacts`, `channel_connections.name`
- [5. Каналы, «Несколько каналов и имена»](../../architecture/05-channels.md#несколько-каналов-и-имена) — имя канала в списках и треде
- [12. Структура репозитория](../../architecture/12-repo-structure.md) — `app/(app)/inbox/`
- Интерактивный макет UI: `docs/references/ui-mockup.html` — ориентир по компоновке

Существенные факты:

- E-001/T-07 свёрстал инбокс «Сообщения» (и все остальные разделы) на mock-данных
  по макету `docs/references/ui-mockup.html`. Этот тикет не строит UI с нуля:
  существующие компоненты подключаются к реальным данным БД, mock-данные раздела
  убираются.
- Данные читаются publishable-клиентом под RLS пользователя (E-001).
- T-03 наполняет таблицы через вебхуки; для локальной разработки и ревью нужны
  сиды — расширить сиды E-001 (T-06 эпика E-001) диалогами и сообщениями
  минимум двух каналов одной платформы.
- **Панель черновика не подключать** — реальные черновики приходят в этапе 2;
  панель остаётся mock-заглушкой из E-001/T-07 (поле ввода ответа — этап 3,
  тоже не подключать).
- Комментарии (`kind = comments`) — этап 5: пункт меню «Комментарии» может быть
  заглушкой, экран не делать.
- Вложения: индикатор «вложение» без превью (открытый вопрос №4 эпика).
- Realtime-обновления — следующий тикет T-06; здесь достаточно server-rendered
  данных, но компоненты проектировать так, чтобы T-06 добавил подписку без
  переписывания.

## Шаги реализации

1. `app/(app)/inbox` — компоновка по §10 уже свёрстана в E-001/T-07 (список
   диалогов слева, тред в центре; на мобильном — список, тап открывает тред
   отдельным экраном): перевести раздел с mock-данных на реальные данные БД.
2. Список диалогов: сортировка по `last_incoming_at` убыв.; каждый элемент —
   имя контакта, превью последнего сообщения, время, бейдж `channel_connection.name`,
   счётчик непрочитанного. Пустое состояние («подключите канал» со ссылкой на
   Настройки → Каналы, если подключений нет).
3. Тред: сообщения диалога по времени, входящие визуально отличимы (исходящих
   пока нет), шапка — контакт + бейдж канала. Открытие треда сбрасывает счётчик
   непрочитанного диалога.
4. Фильтр по каналу: параметр (например, `?channel=<id>`) сужает список до одного
   подключения.
5. Навигация: в левом меню (десктоп) пункт «Сообщения» с суммарным счётчиком
   непрочитанного и расхлопом — список каналов workspace под пользовательскими
   именами со счётчиками; клик по каналу = фильтр. Мобильная нижняя панель —
   иконка «Сообщения» с бейджем. Остальные пункты меню (Дашборд, Комментарии,
   Контакты) — остаются mock-каркасом из E-001/T-07, без подключения к БД.
6. Расширить сиды: два канала одной платформы с разными именами, несколько
   диалогов и сообщений, ненулевые счётчики непрочитанного.
7. Тесты: юнит/интеграционные на запросы данных инбокса (список отсортирован,
   фильтр по каналу, сброс непрочитанного); RLS-negative — чужой workspace
   не виден (можно опереться на инфраструктуру тестов E-001).

## Критерии приёмки

- [ ] Список показывает диалоги всех каналов workspace с бейджем имени канала — два канала одной платформы различимы
- [ ] Тред открывается, сообщения в хронологическом порядке, счётчик непрочитанного сбрасывается
- [ ] Фильтр по каналу работает из расхлопа меню и по URL
- [ ] Суммарный счётчик у пункта «Сообщения» и счётчики по каналам совпадают с данными БД
- [ ] Мобильная компоновка: нижняя панель, список → тред → назад
- [ ] Пустые состояния: нет подключений / нет диалогов
- [ ] Панель черновика — только mock-заглушка из E-001/T-07; реальных черновиков и отправки ответов нет (этапы 2–3)

## 🔧 Отчёт разработчика

### Что сделано

**Слой данных — `lib/db/inbox.ts` (новый файл).** Типизированные запросы к
реальному Supabase под тем же соглашением, что и `lib/db/channel-connections.ts`
(T-04): каждая функция — чистая функция от переданного `SupabaseClient` +
`workspaceId` (+ уже загруженного списка `channels`), RLS — источник истины,
явные фильтры `workspace_id` — defense in depth. Возвращает view-модели ровно
той формы, что и `lib/mock` (`ConversationListView`, `ThreadView`,
`ChannelFilterView`) — это и есть задуманный путь миграции, зафиксированный в
докстринге `lib/mock/index.ts`: «форма моделей представления останется
прежней». `category` везде `null`, `debounceNote`/`draft` — `null`: категорий
и AI-черновиков с реальными данными пока нет (вне скоупа, см. «Существенные
факты» тикета и «Вне скоупа» эпика).

Функции: `getInboxNavigationCounters` (суммарный + по-канальный unread для
меню), `getChannelFiltersView` (то же для мобильных чипов), `getConversationListView`
(список диалогов, сортировка `last_incoming_at desc`, опциональный фильтр по
`channel_connection_id`), `getThreadView` (тред: сообщения по времени,
контакт, канал, `replyWindowLabel` из `capabilities.responseWindowHours`),
`markConversationRead` (сброс `unread_count`). Превью последнего сообщения и
полный тред строятся без N+1 — по одному bulk-запросу `messages` на список
разговоров / на тред, агрегация на стороне JS (тот же приём, что уже
использует `lib/mock/index.ts`'s `getDashboard`; на масштабе «сотни
workspace'ов» — адекватно, без Postgres-вьюхи).

**Экран `app/(app)/(shell)/inbox/page.tsx`** переведён с mock (`lib/mock`) на
реальные данные: авторизованный пользователь → workspace →
`listChannelConnections` → список/тред/фильтры каналов через `lib/db/inbox.ts`.
Убран фильтр/бейдж категории (`CategoryFilter`, `CategoryChip`,
`getCategoryFilterOptions`) — реальных категорий ещё нет, ни у одной
conversation/message `category_id` не заполняется на этом этапе (см.
«Отклонения» ниже). Добавлены два разных пустых состояния: «нет
подключённых каналов» (со ссылкой на `Настройки → Каналы`, критерий приёмки)
и «нет диалогов» (текст зависит от того, применён ли фильтр по каналу).
Индикатор вложения заменён с «фото · {имя}» на просто {имя файла или
«вложение»} — открытый вопрос №4 эпика говорит об индикаторе «вложение», а не
только «фото» (реальные вложения — любого типа, не обязательно фото).
Панель черновика (`DraftPanel`) больше не зависит от `thread.draft` (у
реальных тредов он `null`) — рендерится всегда, с константой-заглушкой
`MOCK_DRAFT_STUB` (нейтральный текст «здесь появится черновик…», а не
выдуманный ответ на конкретное сообщение) — так выполняется требование
тикета «панель остаётся mock-заглушкой из E-001/T-07», не просто «пропадает».

**Сброс счётчика непрочитанного при открытии треда** — `app/(app)/(shell)/inbox/actions.ts`
(server action `markConversationReadAction`, тонкая обвязка по образцу
`settings/channels/actions.ts`) + `app/(app)/(shell)/inbox/mark-thread-read.tsx`
(клиентский компонент `MarkThreadRead`, ничего не рендерит, вызывает action в
`useEffect` при монтировании/смене `conversationId`, затем `router.refresh()`).
Специально **не** делается прямой записью внутри рендера серверного
компонента `InboxPage`: это GET, а `<Link>` может его префетчить при наведении
на диалог, который пользователь не открывал — GET не должен иметь побочных
эффектов. `useEffect` срабатывает только при реальном монтировании в браузере.

**Меню (Sidebar/Tabbar) — счётчик и расхлоп пункта «Сообщения» на реальных
данных.** `app/(app)/(shell)/layout.tsx` теперь дополнительно грузит
`listChannelConnections` + `getInboxNavigationCounters` и передаёт результат
как новый проп `messagesCounters` в `Sidebar`/`Tabbar`. Остальные разделы
(Дашборд, Комментарии, Контакты) — по-прежнему на `counters` из `lib/mock`
(вне скоупа тикета и эпика). Чтобы это не «протекло» в разделы Комментарии/
Контакты (их расхлоп в меню использует тот же компонент, но должен
показывать mock-каналы, а не реальные workspace_id) — `Sidebar` резолвит
список каналов для расхлопа по секции: `inbox` → `messagesCounters.channels`
(реальные), остальные секции → `counters.channels` (mock), см.
`subListChannelsFor()`. Типы `InboxNavCounters`/`InboxNavChannelCounter`
объявлены в `_components/navigation.ts` — не импортируются из

локально в клиентском слое — тот же приём, что уже применён в
`settings/channels/channels-panel.tsx` для `ChannelConnectionRow`.

**Расширение типов `Platform` (`lib/mock/types.ts`).** Реальные
`channel_connections` могут быть любой из 4 платформ (`ChannelPlatform` —
telegram/whatsapp/instagram/facebook), а мок-каркас (`lib/mock`) до этого

### Отклонения от плана тикета

1. **Категория и фильтр по категории убраны из инбокса**, хотя в
   исходном mock-варианте экрана (E-001/T-07) они были. Тикет T-05 их вообще
   не упоминает (ни в шагах, ни в критериях приёмки), а реальных категорий
   пока нет: `workspace-bootstrap` не создаёт дефолтную категорию (проверено
   по `lib/workspace-bootstrap.test.ts`), классификация — часть AI-подсистемы,
   вне скоупа этого эпика. Показывать `CategoryFilter` с пустым списком или
   опираться на несуществующие данные значило бы изобретать функциональность
   вне скоупа — поэтому компонент и бейджи убраны из `inbox/page.tsx`, а
   `category` в `lib/db/inbox.ts` всегда `null`. Компонент `CategoryFilter`
   не удалён из кодовой базы — остаётся доступен и рабочим для комментариев
   и других разделов на mock-данных.
2. **Панель черновика — не «пропадает», а показывает нейтральную
   заглушку.** Прочитал требование «панель остаётся mock-заглушкой из
   E-001/T-07» буквально: критерий приёмки формулирует это как утверждение
   о видимом состоянии панели («Панель черновика — только mock-заглушка»),
   а не как «черновиков нет → панели нет». Реальные `drafts` для тредов не
   существуют (реальная генерация — этап 2), поэтому вместо
   per-conversation авторского mock-текста (который выглядел бы как
   настоящий сгенерированный ответ на конкретное сообщение конкретного
   клиента) показывается один и тот же нейтральный текст-плейсхолдер
