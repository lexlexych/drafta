# T-07. Executive summary — ручные шаги

> Этот тикет выполняет **человек** после завершения всех dev-тикетов эпика.
> Агенты сюда только дописывают шаги. Формат шага: зачем → что сделать → как проверить.

## Предусловия

- Dev-тикеты T-01–T-06 в статусе `done`.
- Эпик E-001 завершён: прод задеплоен на Vercel (fra1), регистрация работает,
  DPA у Zernio **запрошен** (E-001/T-08, шаг 8).
- Аккаунт Zernio (или готовность его создать) и доступ к их дашборду.
- Реальный Telegram-аккаунт бизнеса для подключения + личный аккаунт для проверки.

## Шаги

### 1. Подписать DPA Zernio (входное условие этапа 1)

- **Зачем:** без подписанного DPA пропускать реальные переписки через Zernio
  нельзя — GDPR-цепочка ([15.2](../../architecture/15-compliance-gdpr.md#122-субпроцессоры-и-данные));
  это зафиксированное входное условие [этапа 1](../../architecture/16-rollout-plan.md#этап-1--zernio-контур-входящие-2-4-дня).
- **Что сделать:** довести до конца запрос из E-001: получить DPA через Trust Center
  Zernio (trust.zernio.com, под NDA), подписать; зафиксировать ответы на вопросы
  §15.2 (их субпроцессоры, локация обработки, SCC/DPF, ретенция контента).
- **Проверка:** подписанный DPA сохранён; ответы на вопросы §15.2 записаны.
  Если ответы неприемлемы — остановиться и пересмотреть провайдера (см. §17).

### 2. Zernio: API-ключ и вебхук с секретом

- **Зачем:** роут `api/webhooks/zernio` должен получать вебхуки и проверять их
  подпись ([13](../../architecture/13-environments-secrets.md#секреты-vercel-env)).
- **Что сделать:** в дашборде Zernio создать/скопировать API-ключ
  (`ZERNIO_API_KEY`) и настроить вебхук: URL `https://<прод-домен>/api/webhooks/zernio`,
  секрет подписи (`ZERNIO_WEBHOOK_SECRET`) — сгенерировать/скопировать.
  Значения секретов никуда не коммитить.
- **Проверка:** тестовая доставка из дашборда Zernio (если есть кнопка) или первое
  живое событие возвращает 200 — видно в логах Vercel и в таблице `webhook_events`.

### 3. Env-переменные в Vercel и локально

- **Зачем:** адаптер читает `ZERNIO_WEBHOOK_SECRET` (подпись) и `ZERNIO_API_KEY`
  (понадобится с этапа 3, задаём сразу).
- **Что сделать:** Vercel → Settings → Environment Variables: добавить
  `ZERNIO_API_KEY`, `ZERNIO_WEBHOOK_SECRET` для Production (Preview — по желанию),
  сделать redeploy. Локально — дописать те же переменные в `.env.local`.
- **Проверка:** после redeploy вебхук с валидной подписью принимается (200),
  с невалидной — отклоняется (401).

- **Доп. шаг из T-03 (обнаружен разработчиком):** вебхук-роут (`lib/inngest/client.ts`,
  `lib/inngest/events.ts`) уже эмитит `interaction/received` через Inngest SDK —
  **зачем:** без `INNGEST_EVENT_KEY` (и `INNGEST_SIGNING_KEY` для будущего `serve()`,
  см. [13. Окружения, секреты](../../architecture/13-environments-secrets.md#секреты-vercel-env))
  эмиссия в проде будет постоянно fail-safe отваливаться (событие теряется молча —
  не критично для этого эпика, т.к. обработчиков события ещё нет, но нужно для этапа 2).
  **Что сделать:** создать приложение в Inngest (inngest.com), получить
  `INNGEST_EVENT_KEY`/`INNGEST_SIGNING_KEY`, добавить в Vercel env (Production) и
  `.env.local`, подключить интеграцию Inngest↔Vercel. Не блокирует финальную проверку
  этого эпика (можно сделать вместе с началом этапа 2). **Проверка:** событие
  `interaction/received` видно в дашборде Inngest после входящего вебхука.

### 4. Подключить реальный Telegram в Zernio и создать канал в приложении

- **Зачем:** критерий этапа 1 проверяется на реальном Telegram-сообщении.
- **Что сделать:** в дашборде Zernio привязать Telegram-аккаунт бизнеса
  (по их инструкции), скопировать внешний ID аккаунта. В приложении:
  Настройки → Каналы → добавить подключение: платформа Telegram, внешний ID
  из Zernio, имя (например, «Telegram Магазин»).
- **Проверка:** канал в списке со статусом «активен»; внешний ID совпадает
  с тем, что Zernio присылает в вебхуках.

### 5. (Опционально) Туннель для локальной отладки вебхуков

- **Зачем:** видеть живые вебхуки на локальном стеке
  ([13. Локальная разработка](../../architecture/13-environments-secrets.md#локальная-разработка)).
- **Что сделать:** `cloudflared tunnel --url http://localhost:3000` (или ngrok);
  URL туннеля + `/api/webhooks/zernio` временно указать вебхуком в Zernio
  (dev-настройка/второй endpoint, если Zernio позволяет).
- **Проверка:** сообщение в Telegram появляется в локальном инбоксе.

### 6. Сверить живые payload'ы с фикстурами адаптера

- **Зачем:** формат Zernio в тикетах основан на допущениях (открытый вопрос №1);
  «первый контакт с живым API» — главный риск этапа ([17. Риски](../../architecture/17-risks.md)).
- **Что сделать:** после первых живых вебхуков сравнить записи `webhook_events`
  (сырой payload) с фикстурами в `lib/channels/zernio/`; при расхождениях —
  завести доработку адаптера (новый тикет/эпик-фикс) и обновить фикстуры
  реальными payload'ами (обезличив персональные данные).
- **Проверка:** живой payload парсится без ошибок обработки в `webhook_events`
  (нет записей с ошибкой парсинга).

## Финальная проверка эпика

Критерий этапа 1 из [плана внедрения](../../architecture/16-rollout-plan.md#этап-1--zernio-контур-входящие-2-4-дня):

1. Открыть инбокс «Сообщения» на проде.
2. С личного Telegram написать сообщение подключённому аккаунту.
3. Сообщение появляется в инбоксе **за секунды, без перезагрузки**, у диалога —
   бейдж с именем канала («Telegram Магазин»), счётчик непрочитанного вырос.
4. Открыть тред — текст на месте, счётчик сбросился.
5. В `webhook_events` — одна обработанная запись; повторная доставка того же
   события (ретрай Zernio, если можно вызвать) не создаёт дубля сообщения.
