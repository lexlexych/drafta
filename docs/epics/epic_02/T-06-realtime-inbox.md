# T-06. Realtime-обновления инбокса

## Цель

Открытый инбокс живёт сам: новое входящее сообщение появляется в списке диалогов
и в открытом треде без перезагрузки страницы, счётчики непрочитанного и порядок
диалогов обновляются — за секунды после прихода вебхука.

## Контекст

Обязательно прочитать перед выполнением:

- [11. Realtime, Web Push, PWA — «Realtime»](../../architecture/11-realtime-pwa.md#realtime) — подписка на `insert`/`update` в `messages` (и `drafts` — позже) текущего workspace
- [6. Модель данных](../../architecture/06-data-model.md) — `messages`, `conversations`
- [16. План внедрения, этап 1](../../architecture/16-rollout-plan.md#этап-1--zernio-контур-входящие-2-4-дня) — критерий «сообщение появляется в инбоксе за секунды»
- [14. Правила вайбкодинга](../../architecture/14-vibecoding-rules.md) — правило 2 (публикация Realtime включается миграцией, не через дашборд)

Существенные факты:

- T-05 построил инбокс на server-rendered данных; этот тикет добавляет клиентскую
  подписку поверх, не переписывая экраны.
- Supabase Realtime (postgres_changes) требует добавить таблицы в публикацию
  `supabase_realtime` — **только миграцией** (правило 2). Подписки должны уважать
  RLS: клиент авторизован publishable-ключом с пользовательской сессией.
- Web Push, `send-push`, `push-digest` — этап 9; здесь только Realtime в открытой
  вкладке.
- `drafts` в подписку не включать — черновиков до этапа 2 нет (архитектура §11
  упоминает их для будущих этапов; добавится тогда же).

## Шаги реализации

1. Миграция: добавить `messages` и `conversations` в публикацию
   `supabase_realtime` (и `replica identity`, если требуется для update-событий).
2. Клиентская подписка в инбоксе: `insert` в `messages` и `insert`/`update`
   в `conversations` текущего workspace (фильтр по `workspace_id`);
   на событие — обновление списка диалогов (порядок, превью, счётчики)
   и открытого треда (новое сообщение появляется в конце).
3. Суммарный счётчик и счётчики каналов в меню обновляются от тех же событий.
4. Жизненный цикл подписки: подписка при монтировании, отписка при уходе со
   страницы; переподписка при разрыве соединения (штатное поведение supabase-js —
   проверить, не изобретать своё).
5. Проверочный сценарий (задокументировать в отчёте): открыть инбокс, отправить
   в вебхук-роут фикстуру (curl/скрипт из T-03) — сообщение появляется в UI без
   перезагрузки; для не открытого диалога растёт счётчик.
6. Тесты: юнит на обработчик Realtime-события (обновление локального состояния
   списка/треда/счётчиков); сквозная авто-проверка Realtime не требуется —
   ручной сценарий из шага 5 обязателен для ревью.

## Критерии приёмки

- [ ] Новое входящее (через вебхук-роут) появляется в открытом списке диалогов без перезагрузки — за секунды
- [ ] В открытом треде сообщение дописывается в конец без перезагрузки
- [ ] Счётчики непрочитанного (диалог, канал, суммарный) обновляются live
- [ ] Таблицы добавлены в публикацию Realtime миграцией; изменений через дашборд нет
- [ ] Подписка отфильтрована по workspace и работает под RLS пользователя (чужие события не приходят — negative-проверка двумя пользователями из сидов)
- [ ] Подписка корректно снимается при уходе со страницы

## 🔧 Отчёт разработчика

### Что сделано

**Миграция — `supabase/migrations/20260720160000_enable_realtime_publication.sql`
(новая).** `alter publication supabase_realtime add table public.messages,
public.conversations;` — единственная схемная правка тикета (правило 2:
только миграция, не дашборд). `drafts` сознательно не добавлен (тикет:
«черновиков до этапа 2 нет»). REPLICA IDENTITY оставлен по умолчанию
(только PK) — не тронут: обоснование прямо в комментарии миграции
(логическая репликация Postgres всегда отдаёт полную *новую* строку для
INSERT/UPDATE независимо от replica identity; только *старая* строка
UPDATE/DELETE от него зависит, а обработчики этого тикета читают
исключительно `payload.new`, старая строка нигде не нужна). Проверено на
локальном Supabase: `pg_publication_tables` для `supabase_realtime`
содержит ровно `messages`/`conversations` после `supabase db reset`.

**`lib/realtime/inbox-sync.ts` (новый, НЕ `"server-only"` — исполняется в
браузере).** Ядро клиентской подписки:
- `subscribeToInboxRealtime(supabase, workspaceId, refresh)` — открывает один
  `RealtimeChannel` (`inbox-realtime:<workspaceId>`) с тремя
  `postgres_changes`-подписками ровно по шагу 2 тикета: `INSERT` на
  `messages`, `INSERT` и `UPDATE` на `conversations`, каждая с
  `filter: "workspace_id=eq.<id>"`. Возвращает функцию отписки
  (`supabase.removeChannel(channel)`) — вызывается в `useEffect`-cleanup
  (шаг 4 тикета).
- `createInboxRealtimeHandler`/`isOwnWorkspaceEvent` — обработчик события:
  проверка `payload.new.workspace_id === workspaceId` (defense in depth поверх
  серверного `filter` канала и RLS на публикации — тот же приём, что explicit
  `workspace_id`-фильтры в `lib/db/inbox.ts` из T-05 поверх RLS), затем
  дебаунс 250 мс (константа `DEFAULT_DEBOUNCE_MS`), схлопывающий пачку
  событий (несколько сообщений подряд, insert conversation + следующий
  update от `bump_conversation_unread_count`) в один вызов `refresh()`.
- Реконнект после разрыва соединения — не реализован специально: это штатное
  поведение `supabase-js`/`realtime-js` (автопереподключение с backoff), шаг 4
  тикета прямо просит не изобретать своё; здесь просто не добавлено ничего
  поверх (`.subscribe()` без кастомной retry-логики).

**`app/(app)/(shell)/_components/inbox-realtime-sync.tsx` (новый) +
`layout.tsx` (правка).** Клиентский компонент `InboxRealtimeSync`
подписывается при монтировании (`createBrowserSupabaseClient()` +
`subscribeToInboxRealtime`), отписывается при размонтировании; на событие
вызывает `router.refresh()` — тот же приём, что `inbox/mark-thread-read.tsx`
(T-05): Next.js перезапрашивает серверные компоненты текущего маршрута
свежими данными без полной перезагрузки страницы. Смонтирован в
`ShellLayout` (`<InboxRealtimeSync workspaceId={workspace.id} />`, рядом с
`<Toast />`), а не внутри `inbox/page.tsx` — потому что шаг 3 тикета требует
живого обновления счётчиков меню (Sidebar/Tabbar), которые видны на любом
экране защищённой зоны, не только на `/inbox`; `router.refresh()`
перерисовывает весь текущий маршрут, включая layout, так что один вызов
обновляет и счётчики, и (когда пользователь на `/inbox`) список/тред разом.
Эффект подписки завязан только на `[workspaceId]`: `router.refresh` читается
через `useRef`, обновляемый отдельным эффектом (а не присваиванием в теле
компонента — так делать `eslint`-правило `react-hooks/refs` запрещает
«мутацию ref во время рендера»), чтобы нестабильная по идентичности ссылка
на `router` между рендерами не пересоздавала сокет без необходимости.

**Почему реакция на событие — `router.refresh()`, а не ручной патч
локального состояния списка/треда/счётчиков.** `lib/db/inbox.ts` (T-05)
строит `ConversationListView`/`ThreadView`/`InboxNavigationCounters` джойнами
`contacts`/`channel_connections` поверх `messages`/`conversations` плюс
форматированием (цвет аватара, метки времени, окно ответа). Сырой
`postgres_changes`-payload содержит только столбцы изменившейся таблицы —
воссоздать вью-модель из него на клиенте значило бы завести второй источник
истины и дублировать логику `lib/db/inbox.ts` (риск рассинхрона); для
совсем нового диалога (первое сообщение от нового контакта) локально патчить
вообще нечего — эта строка ещё не присутствует в состоянии клиента. Повторный
запрос серверных компонентов маршрута — тот же принцип, что уже установлен
`mark-thread-read.tsx` в T-05 для «данные на сервере изменились → обновить
экран без полной перезагрузки», с одним источником истины. Это решение
задокументировано и в докстринге `lib/realtime/inbox-sync.ts`.

**Тесты:**
- `lib/realtime/inbox-sync.test.ts` (новый, 9 тестов) — «юнит на обработчик
  Realtime-события» из шага 6 тикета: `isOwnWorkspaceEvent` (совпадающий и

  `subscribeToInboxRealtime` (с фейковым `supabase`-клиентом) — открывается

### Отклонения от плана тикета

1. **Реакция на Realtime-событие — `router.refresh()`, а не ручной патч
   клиентского состояния списка/треда/счётчиков полями из
   `postgres_changes`-payload'а.** Обоснование — раздел «Что сделано» выше.
   Критерии приёмки («список обновляется», «сообщение дописывается в конец»,
   «счётчики обновляются live») выполняются по факту (подтверждено сквозной
   проверкой), но механизм — не буквально «патч state на клиенте», как можно
   прочитать формулировку шага 2 тикета. «Юнит на обработчик Realtime-события,
   обновление локального состояния» из шага 6 реализован как тесты
   `createInboxRealtimeHandler`/`subscribeToInboxRealtime` (решение о том,
   *когда* и *для какого workspace* планировать обновление — дебаунс-таймер,
   это и есть «локальное состояние» обработчика) — если ревьюер сочтёт, что
   тикет требовал именно реализации клиентского reducer'а поверх сырых строк
   `messages`/`conversations`, это отдельная, значительно более крупная
   переработка (нужно дублировать джойны/форматирование `lib/db/inbox.ts` на
   клиенте или гонять доп. запросы за контактом/каналом на каждое событие).
2. **Дебаунс 250 мс перед `refresh()`** — не упомянут в тикете явно, добавлен
   как инженерное решение (шаг 2 подразумевает возможную пачку событий:
   несколько сообщений подряд, insert+update по одному диалогу от одного
   вебхука) — снижает число RSC-запросов на пачку событий до одного,
   незаметно для критерия «за секунды».
3. **REPLICA IDENTITY не менялся** — тикет в шаге 1 предлагает «и replica
   identity, если требуется для update-событий»; по факту не потребовался
   (обоснование — в комментарии миграции и в разделе «Что сделано» выше):
   постгрес всегда шлёт полную новую строку по логической репликации, а
   обработчики этого тикета читают только `payload.new`. Если у ревьюера
   другое мнение по этому пункту — правка тривиальна (один `alter table …
   replica identity full;` на каждую из двух таблиц).

### Вне скоупа

- `drafts` в публикацию Realtime — этап 2 (тикет и эпик прямо это исключают).
- Web Push/Serwist/PWA — этап 9, не затронуто.
- Ручной патч клиентского состояния вместо `router.refresh()` — см.
  «Отклонения», п. 1; если понадобится позже (например, ради анимации
  появления новой строки списка без мигания всего дерева), это отдельная
  задача поверх уже работающей Realtime-подписки этого тикета.
- Индикатор «переподключение»/офлайн-статус UI — не запрошен ни тикетом, ни
  архитектурой (§11 явно ограничивает офлайн-возможности PWA оболочкой,
  «данные всегда из сети»).

## 🔍 Ревью

### Вердикт 2026-07-21: `CHANGES_REQUESTED`

1. **Ошибки и статус подписки полностью игнорируются.**
   `lib/realtime/inbox-sync.ts:114-131` вызывает `.subscribe()` без status callback.
   `CHANNEL_ERROR`, `TIMED_OUT` и `CLOSED` не попадают ни в лог, ни в UI, ни в
   retry/диагностику. При отказе канала приложение выглядит рабочим,
   но больше никогда не обновляется. Это не позволяет надёжно выполнить
   шаг 4 и является прямой причиной, почему текущий production-отказ невозможно
   локализовать по коду и логам.

2. **После reconnect пропущенные изменения не восстанавливаются.**
   Автопереподключение `supabase-js` восстанавливает канал, но Postgres Changes
   не реплеит события, произошедшие во время разрыва. Код не отслеживает
   повторный `SUBSCRIBED` и не делает контрольный refresh/refetch. Инбокс может
   остаться устаревшим до следующего события или ручной перезагрузки.

3. **Заявленный пользовательский результат не покрыт автотестом.**
   `lib/realtime/inbox-sync.test.ts` проверяет форму мока `.on()` и вызов callback,
   а `app/(app)/(shell)/_components/inbox-realtime-sync.test.tsx` — что мок вызвал
   мок `router.refresh()`. Ни один тест не доказывает, что после реального
   Realtime-события на экране меняются список, тред и счётчики. Требование
   шага 6 о тесте обновления локального состояния фактически заменено более
   слабой проверкой и не защищает главные критерии приёмки.

4. **Cleanup не отменяет отложенный refresh.**
   Таймер создаётся в `createInboxRealtimeHandler` (`lib/realtime/inbox-sync.ts:78-92`),
   но cleanup возвращает только `removeChannel` (`lib/realtime/inbox-sync.ts:133-135`).
   Если компонент демонтирован в 250-мс окне, `router.refresh()` всё равно выполнится
   уже после ухода из shell/logout. Кроме того, обычный trailing debounce может
   откладывать refresh неограниченно при непрерывном потоке событий, что нарушает
   критерий «за секунды». Нужен отменяемый throttle/debounce с `maxWait`.

5. **Открытый тред может показать собственный unread-счётчик.**
   Вебхук увеличивает `conversations.unread_count`, Realtime делает refresh,
   но `MarkThreadRead` не вызывает action повторно для того же `conversationId`
   (`app/(app)/(shell)/inbox/mark-thread-read.tsx:23-35`). Формулировка тикета явно отличает
   открытый диалог от неоткрытого; текущая схема этого не обеспечивает.

### Follow-up 2026-07-21: observability и reconnect

- `.subscribe(statusCallback)` теперь фиксирует успешную подписку, ошибки,
  timeout/закрытие и восстановление канала в browser console; компонент также
  публикует техническое DOM-событие `drafta:inbox-realtime-status`, чтобы статус
  можно было подключить к UI или клиентскому мониторингу без изменения transport-слоя.
- После повторного `SUBSCRIBED` выполняется немедленный `router.refresh()`:
  события, пропущенные во время разрыва WebSocket, восстанавливаются чтением
  актуального состояния из БД.
- Cleanup теперь отменяет отложенный refresh, а debounce ограничен `maxWait=1000ms`,
  чтобы непрерывный поток событий не откладывал обновление бесконечно.
- Попытка ограничить Postgres Changes payload полями `id` и `workspace_id`
  была отменена следующим follow-up: remote Realtime отклоняет сочетание
  column `select` и фильтра `workspace_id`. Payload по-прежнему используется
  только как сигнал; транспортную минимизацию нужно реализовать через Broadcast.
- По прямому указанию пользователя новые тесты на этом follow-up не добавлялись,
  test suite не запускался; временная синхронизация mock-ожиданий с `select`
  отменена вместе с самим `select` в следующем follow-up.

### Follow-up 2026-07-21: исправление отклонённой подписки

Ручная проверка browser WebSocket выявила корневую ошибку, которая не попадала
в callback `.subscribe()`: Realtime отправил отдельный system frame со статусом
`error` и сообщением `invalid column for filter workspace_id` для подписки
`UPDATE conversations` с `select: ["id", "workspace_id"]`.

- `select` удалён из всех трёх Postgres Changes bindings; фильтрация по
  `workspace_id` и RLS сохранены.
- Добавлен listener `system`, который переводит статус в `error` и логирует
  полный текст отказа Postgres Changes. Теперь успешный join WebSocket-канала
  не маскирует отклонённую сервером replication binding.
- Новые тесты не добавлялись, test suite по указанию пользователя не запускался.
