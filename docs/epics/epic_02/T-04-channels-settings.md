# T-04. Настройки → Каналы: подключения с именами

## Цель

В защищённой зоне работает раздел «Настройки → Каналы»: список подключений workspace
с пользовательскими именами, добавление Zernio-подключения (платформа, внешний ID
аккаунта, имя), переименование и отключение. Workspace может держать несколько
каналов одной платформы, различимых по именам.

## Контекст

Обязательно прочитать перед выполнением:

- [5. Слой абстракции каналов, «Несколько каналов и имена»](../../architecture/05-channels.md#несколько-каналов-и-имена) — зачем имя и куда оно протекает
- [6. Модель данных, channel_connections](../../architecture/06-data-model.md#channel_connections) — поля: name, провайдер, платформа, внешний ID, capabilities, статус; уникальность (workspace, провайдер, внешний ID)
- [10. UI, «Разделы настроек»](../../architecture/10-ui.md#разделы-настроек) — раздел «Каналы»
- [12. Структура репозитория](../../architecture/12-repo-structure.md) — `app/(app)/settings/`
- [2. Глоссарий](../../architecture/02-glossary.md) — `channel_connection`, в коде никогда «account»
- [14. Правила вайбкодинга](../../architecture/14-vibecoding-rules.md) — правила 1, 4

Существенные факты:

- E-001 дал auth, защищённую зону `app/(app)/` и таблицу `channel_connections`
  с RLS — пользовательские запросы идут через publishable-клиент под RLS.
- E-001/T-07 свёрстал раздел «Настройки» (включая экран каналов) на mock-данных
  по макету `docs/references/ui-mockup.html` — экран дорабатывается из этого
  каркаса: mock-данные раздела заменяются реальным CRUD, вёрстку с нуля не писать.
- **Открытый вопрос №1 эпика:** привязка аккаунта соцсети происходит на стороне
  Zernio (их дашборд); в нашем UI подключение создаётся вводом внешнего ID аккаунта
  вручную. Если адаптер реализует опциональную `getConnectUrl` (T-01/T-02) —
  показать кнопку-ссылку «Подключить в Zernio», иначе просто поле ввода
  с подсказкой, где взять ID.
- Capabilities при создании заполняются дефолтами платформы из
  `lib/channels/capabilities.ts` (T-01).
- Отключение = смена статуса (например, `disconnected`), **не удаление** строки:
  удаление каскадно стёрло бы диалоги и сообщения. Полное удаление подключения —
  вне скоупа эпика.
- Credentials для Zernio пусты (ключи — на уровне окружения, §13) — поле
  в форме не нужно.

## Шаги реализации

1. Server actions (или route handlers) для операций: создать подключение
   (провайдер `zernio`, платформа из списка поддерживаемых, внешний ID, имя),
   переименовать, отключить/включить. Валидация: имя непустое; дружелюбная ошибка
   при нарушении уникальности (workspace, провайдер, внешний ID).
2. Страница `app/(app)/settings/channels`:
   - список подключений: имя, платформа, статус, внешний ID;
   - форма добавления; capabilities проставляются дефолтами платформы;
   - переименование (inline или диалог);
   - отключение с подтверждением; отключённый канал визуально отличим.
3. Каркас раздела настроек, если его ещё нет: `app/(app)/settings` с навигацией
   по разделам (пока активен только «Каналы»; остальные — заглушки-ссылки без
   содержимого, приходят в следующих эпиках).
4. Тесты на server actions: создание двух подключений одной платформы с разными
   внешними ID проходит; дубль внешнего ID — ошибка; переименование и смена
   статуса работают; пользователь чужого workspace не видит и не меняет
   подключения (RLS, negative-тест).

## Критерии приёмки

- [ ] Два подключения одной платформы с разными именами создаются и оба видны в списке
- [ ] Дубль (workspace, провайдер, внешний ID) отклоняется с понятной ошибкой
- [ ] Переименование меняет `name`; отключение меняет статус, строка не удаляется
- [ ] Capabilities нового подключения заполнены дефолтами платформы (видно в БД)
- [ ] Доступ только у участников workspace (RLS подтверждена negative-тестом)
- [ ] В коде и схеме нет слова `account`; UI-лейблы — на усмотрение, код — по глоссарию
