# T-03. Отправки DM и комментариев с ручным повтором и сверкой результата

## Цель

Три отправки выполняются Workflow; пользователь видит ошибку и безопасно повторяет существующее сообщение/ответ.

## Контекст

[План, §2, §4–5](../../plans/inngest-to-vercel-workflow.md), [каналы](../../architecture/05-channels.md), [модель](../../architecture/06-data-model.md), [потоки, отправки](../../architecture/07-data-flows.md), [UI](../../architecture/10-ui.md), T-02. Исходники: lib/inngest/functions/send-message.ts, send-comment.ts, send-comment-private-reply.ts и их pipelines; действия inbox/comments.

Общие обязательные источники: [глоссарий](../../architecture/02-glossary.md), [правила](../../architecture/14-vibecoding-rules.md). Прямое решение пользователя заменяет требования Inngest и автоматических retry: основное приложение переходит на Vercel Workflow; архитектуру синхронизирует T-07. `website/` исключён из изменений.

## Шаги реализации

1. Создать sendMessageWorkflow, sendCommentWorkflow, sendCommentPrivateReplyWorkflow в отдельных файлах lib/workflows/. Вынести общую бизнес-логику из lib/inngest в предметные модули; провайдерный код оставить lib/channels. БД-контекст загружать и использовать внутри use step.
2. Подключить start в действующих actions через T-02, сохранив порядок отправки, workspace limit, проверки подключения, членства и capability/окна ответа. Каждый бизнес-шаг maxRetries = 0; проверить скрытые HTTP retry.
3. Реализовать claim внешней отправки до обращения к провайдеру, стабильный ключ идемпотентности там, где он поддерживается. Разделить известную неудачу и неизвестный результат. Webhook/remote ID/status восстанавливают статус без повторной отправки.
4. Для обычных сообщений и private reply подключить имеющийся UI повтора. Добавить retry server action и кнопку у своего неотправленного публичного ответа на комментарий: повторяется существующая строка, новая не создаётся.
5. Добавить UX uncertain: «Проверить статус» при доступной сверке; иначе предложить проверить канал и отдельное явное действие после проверки. Сервер также запрещает слепой retry. При закрытом окне private reply показывать понятную причину.
6. Покрыть успех провайдера + ошибку БД: хранить возможность сверки и не вызывать send повторно. Подготовить идемпотентный запуск дочерней отправки для автоответа в T-04.

## Критерии приёмки

Ниже — итоговый acceptance, включая живое окружение; локальная реализация завершена, подтверждение полного сценария отмечается при T-08.

- [ ] Все три workflow реально вызываются из существующих actions, входы/выходы содержат только ID и технические статусы. Inngest не получает параллельное событие для этих операций.
- [ ] Ошибка отправки даёт один вызов provider API; кнопка повторяет существующую запись с новым attempt, не создавая дубль сообщения/комментария.
- [ ] Два клика/вкладки, повтор run и задержанный webhook не создают вторую подтверждённую внешнюю отправку. Последовательность по переписке/посту сохранена.
- [ ] Таймаут и success + DB failure переходят в uncertain/сверку; проверка статуса не вызывает send. Confirmed success не допускает resend.
- [ ] Ошибка, retry, uncertain и невозможность private reply отображаются в реальном UI, включая обновление второй вкладки; сервер проверяет права.
- [ ] Сохранены вложения, нормализация ID, delivery callbacks и существующие adapter contracts; исходные tests перенесены, не удалены ради зелёного прогона.

## Definition of Done

`pnpm exec vitest run <send pipeline, inbox/comments actions и UI tests>`, `pnpm exec tsc --noEmit`, `pnpm lint`; smoke трёх отправок на фикстурах: fail → UI retry → sent, timeout → status check без send, двойной клик. Обязательный smoke после фичи: `pnpm exec vitest run 'app/(app)/(shell)/smoke.test.tsx' --maxWorkers=1 --no-file-parallelism`.

## 🔧 Отчёт разработчика

Три отправки перенесены в lib/workflows; бизнес-пайплайны сохранены в lib/jobs. Сохранённый ID результата завершает запись без повторного send. Неизвестный исход отображается как uncertain и требует подтверждения проверки канала. WorkflowErrors добавлен в переписку и комментарии; сервер проверяет workspace. Внешняя доставка не имеет абсолютной гарантии exactly-once при сбое провайдера.

Проверки и ограничения общего интеграционного прогона записаны в [T-08](T-08-executive-summary.md#результаты-локальных-проверок-2026-09-21). Непроверенные живые сценарии остаются критериями ручного acceptance.
