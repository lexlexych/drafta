# T-08. Executive summary — ручные шаги

> Этот тикет выполняет **человек** после завершения всех dev-тикетов эпика.
> Агенты сюда только дописывают шаги. Формат шага: зачем → что сделать → как проверить.

## Результаты локальных проверок — 2026-09-21

Dev-тикеты T-01–T-07 реализованы. Production не переключён.

- `pnpm exec vitest run --maxWorkers=2`: **111 файлов / 871 тест прошли**, 6 файлов / 45 DB-backed тестов пропущены из-за отсутствия работающей Supabase.
- Дополнительно `pnpm exec vitest run lib/workflows/background.test.ts --maxWorkers=1 --no-file-parallelism`: **5 тестов прошли**. Файл добавлен после начала общего прогона.
- Общий прогон включает все **32 smoke-теста** основного интерфейса; отдельный профильный прогон ранее: 15 файлов / 114 тестов, успешно.
- `pnpm exec tsc --noEmit`, `pnpm lint` и дополнительный lint нового background-теста: успешно.
- `pnpm build`: успешно; компилятор обнаружил **13 Workflow и 26 steps**, служебные маршруты и оба Cron присутствуют. TypeScript-проверка production build также успешна.
- Настоящая новая SQL-миграция исполнена в PGlite: 9 тестов операций, RLS, fencing, lease, лимитов, повторов и импорта прошли. Это минимальная схема-фикстура, не полный Supabase/PostgREST/Storage.
- Docker Desktop Linux engine недоступен (отсутствует named pipe). `pnpm test:rls` и `pnpm exec supabase test db` на полной изолированной Supabase **не выполнены**; применить миграции и выполнить их в шаге 1. Облачный target для тестов не использовался.
- Живой SDK start/status/cancel, реальные провайдеры, история/retention/регион Workflow и поведение двух браузеров требуют staging acceptance ниже; автоматические тесты SDK используют моки.

Точные пути, настройки и порядок переключения/rollback: [инструкция Workflow](../../integrations/vercel-workflow.md). Миграция: `supabase/migrations/20260919100000_workflow_operations.sql`. Cron: `/api/cron/ai-request-log` и `/api/cron/publication-assets`; секрет `CRON_SECRET`. Облачные шаги ниже не отмечены выполненными.

## Предусловия

Доступ к основному Vercel-проекту drafta, Supabase dev/prod и приложению Inngest основного продукта; все dev-тикеты E-004 завершены. Лендинг website/ имеет отдельные настройки, их не менять. Действующие подключения каналов, LLM и VAPID сохраняются. Источники: [план](../../plans/inngest-to-vercel-workflow.md), [окружения](../../architecture/13-environments-secrets.md), отчёты T-01–T-07.

Разработчики дописывают ниже конкретные endpoint paths, фактические настройки закреплённой версии SDK и команды, выявленные при реализации. Не вносить значения секретов в тикет.

## Шаги

### 1. Подготовить тестовое окружение и проверить миграции

- **Зачем:** проверить операции, RLS и блокировки до переключения production.
- **Что сделать:** выбрать отдельный локальный/разрешённый dev Supabase target; сверить идентификатор проекта и разрешённую test allowlist. Применить только миграции из supabase/migrations штатным CLI/CI. Не выполнять SQL-тесты на production. Прогнать команды из отчётов T-02/T-07, включая SQL, RLS и конкурентные сценарии; все непрогнанные разработчиком проверки перечислить здесь.
- **Проверка:** новые таблицы/RPC применены, чужой workspace не имеет доступа, двойной retry даёт один attempt, старый fencing token не финализирует новую попытку.

### 2. Проверить Workflow, регион и ограничения проекта

- **Зачем:** состояние Workflow и обработка должны находиться в fra1; тариф должен поддерживать используемый Cron и длительность шагов.
- **Что сделать:** в Vercel открыть основной проект → Settings → Functions и сверить fra1; проверить настройки Workflow и фактический регион состояния тестового run по процедуре T-01. Проверить доступность SDK 5.0.0-beta.53 в deployment, поддержку почасового Cron и max duration используемых steps. Условия/ограничения версии сверить по официальной документации из отчёта T-01.
- **Проверка:** облачный тестовый run завершён и отменён поддерживаемым API, подтверждены fra1 выполнения и хранения состояния. Скрин/ссылку на run можно сохранить без контента/секретов. Локальная конфигурация сама по себе не доказательство облачного региона.

### 3. Настроить Cron и проверить наблюдаемость

- **Зачем:** служебные очистки должны запускаться по расписанию и сообщать о постоянных сбоях.
- **Что сделать:** основной Vercel-проект → Settings → Environment Variables: задать CRON_SECRET в нужных окружениях и выполнить deployment. В Cron Jobs проверить два маршрута из vercel.json: AI-логи 0 3 * * *, публикации 17 * * * * (UTC). Значение секрета не копировать в тикет. Проверить выбранный в T-06 способ наблюдения terminal failures.
- **Проверка:** запрос без корректного Bearer secret отклоняется; разрешённый запуск создаёт Workflow. Дубликат расписания безопасен; в failure-сценарии не более 2 дополнительных попыток. Активные файлы/задания не удалены.

### 4. Переключить основной продукт и сверить старые запуски

- **Зачем:** исключить параллельную отправку старым Inngest run и новым Workflow.
- **Что сделать:** выполнить конкретную последовательность cutover из T-07. До отключения старой версии завершить либо отменить и сверить её активные Inngest run, особенно спящие автоответы, pending sends и uncertain deliveries. При необходимости ограничить новые действия на короткое окно переключения. Каждую операцию передавать только одному движку; неизвестный результат не отправлять заново. Выполнить deployment новой версии после готовности схемы и сверки.
- **Проверка:** новые операции запускают только Workflow, старые не могут повторить их; delivery/operation статусы согласованы. Старый deployment не удалять, пока на нём нужны исполнения. Процедура rollback из T-07 учитывает уже запущенные Workflow, а не только откат кода.

### 5. Удалить настройки Inngest основного проекта

- **Зачем:** убрать неиспользуемое подключение после успешного переключения.
- **Что сделать:** после шага 4 в основном Vercel-проекте удалить INNGEST_EVENT_KEY/INNGEST_SIGNING_KEY и относящуюся к нему интеграцию. В Inngest отключить только приложение основного продукта после проверки отсутствия активных run. Секреты, интеграцию и приложение website/ оставить.
- **Проверка:** основной deployment работает без ключей Inngest; новый входящий/отправка запускают Workflow. Лендинг продолжает прежнюю отправку заявок.

### 6. Проверить описание обработки данных

- **Зачем:** публичная документация должна отражать хранение истории оркестрации Vercel.
- **Что сделать:** сверить обновлённые app/privacy/page.tsx и главу 15 с фактическими регионами, данными истории и условиями сервиса; подтвердить применимость текущего DPA Vercel и фактическую ретенцию Workflow. Не удалять сведения об Inngest из раздела отдельного лендинга.
- **Проверка:** в истории тестовых Workflow нет сообщений, промптов, контактов, URL, байтов, provider response bodies или секретов; только ID и минимальные технические статусы. Отражены реальные параметры без обещания непроверенной ретенции.

## Финальная проверка эпика

В staging/разрешённом тестовом workspace выполнить:

1. Входящее → инбокс → ручной AI-черновик → управляемая ошибка отправки → UI retry → одно исходящее.
2. Ошибка автоответа до создания сообщения → «Повторить автоответ» в переписке; новый входящий/ручной ответ оператора/Stop не допускают позднюю отправку.
3. Ошибка публичного комментария и private reply → повтор существующего ответа; uncertain → проверка статуса без внешней отправки.
4. Ошибка отдельного слайда → повтор только незавершённого; истёкшие import URL → свежий импорт; один неуспешный канал публикации не повторяет успешный.
5. Фото/миниатюра после ошибки обновляются вручную. Push на успешное устройство не дублируется из-за другого неуспешного устройства; два Cron выполняются с согласованной политикой.
6. Две вкладки/двойной клик не дублируют бизнес-операцию; второй workspace не может читать/retry/cancel чужую. Сбой start и аварийный run не оставляют UI бесконечно busy.
