# T-01. Vercel Workflow SDK: сборка, регион и безопасные границы шагов

## Цель

Основное приложение собирается с закреплённым Workflow SDK; запуск, отмена и политика повторов имеют проверенный серверный контракт.

## Контекст

[План, §6–8](../../plans/inngest-to-vercel-workflow.md), [стек](../../architecture/03-stack.md), [структура](../../architecture/12-repo-structure.md), [окружения](../../architecture/13-environments-secrets.md), [PWA](../../architecture/11-realtime-pwa.md), [GDPR](../../architecture/15-compliance-gdpr.md). Сейчас Next.js 16.2.10, build --webpack, Serwist; SDK Inngest удаляется только в T-07.

Общие обязательные источники: [глоссарий](../../architecture/02-glossary.md), [правила](../../architecture/14-vibecoding-rules.md). Прямое решение пользователя заменяет требования Inngest и автоматических retry: основное приложение переходит на Vercel Workflow; архитектуру синхронизирует T-07. `website/` исключён из изменений.

## Шаги реализации

1. Проверить официальные документы и реальные exports/types `workflow@5.0.0-beta.53`; закрепить точную версию в package.json и lockfile. Эта линия выбрана ради хранения состояния в fra1 (поддержка >=5.0.0-beta.33); 4.x не подходит. Если необходима другая версия, обосновать её совместимость и регион в отчёте.
2. Добавить поддерживаемую интеграцию в next.config.ts вместе с Serwist. Настроить регион выполнения и хранения Workflow fra1 по фактическому API SDK; не считать один regions в vercel.json достаточным доказательством хранения состояния.
3. Создать минимальную инфраструктуру `lib/workflows/`: серверный start/status/cancel, явные retry-константы, безопасный код ошибки. Документировать реальные API и границы use workflow/use step. В workflow не импортировать непосредственно Supabase, Node-only SDK и предметный контент.
4. Проверить proxy.ts и app/sw.ts: служебные маршруты SDK не получают redirect на login и не кэшируются offline; прикладные маршруты операций остаются авторизованными. Исключения максимально узкие.
5. Проверить локальный пример запуска/завершения/отмены и однократный ошибочный бизнес-шаг; не добавлять публичный тестовый endpoint в production. Проверку фактического региона облачного run и ограничений тарифа записать в T-08.

## Критерии приёмки

- [ ] Пакет закреплён точной версией; production build создаёт Workflow/step routes, работает совместно с Serwist; dev-команда проекта поддерживается.
- [ ] Бизнес-шаг с maxRetries = 0 выполняется один раз при ошибке; серверные ошибки сериализуются безопасным кодом. Для фоновых исключений доступен явный лимит 2 дополнительных попытки.
- [ ] Проверены реальные start, get run/status и cancel API. Контракт доступен T-02, нет имитации Workflow через обычный async/fire-and-forget.
- [ ] В workflow/step inputs/outputs тестового контура только ID и технические статусы; нет текста, токенов, URL, байтов, промптов или исходных provider errors.
- [ ] Автоматические проверки региональной конфигурации и служебных маршрутов пройдены; облачные проверки честно отделены в manual summary от локально подтверждённых.

## Definition of Done

`pnpm exec tsc --noEmit`, `pnpm lint`, `pnpm build`; целевые runtime/config tests через `pnpm exec vitest run <созданные test-файлы>`. Локальный smoke запуска, завершения, ошибки и отмены, с конкретными командами и результатом в отчёте. Обязательный smoke после фичи: `pnpm exec vitest run 'app/(app)/(shell)/smoke.test.tsx' --maxWorkers=1 --no-file-parallelism`.
