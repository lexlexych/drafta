# T-02. Клиент LLM в lib/ai: Mistral с fallback на OpenRouter

## Цель

В `lib/ai` работает единая точка вызова LLM: OpenAI-совместимый SDK со сменным
`baseURL`, провайдер выбирается по env-переменным без изменения кода — задан
`MISTRAL_API_KEY` → Mistral (La Plateforme), иначе → OpenRouter
(`OPENROUTER_API_KEY` + `OPENROUTER_MODEL`). Выбор провайдера покрыт юнит-тестами;
прямых обращений к SDK за пределами `lib/ai` нет.

## Контекст

Обязательно прочитать перед выполнением:

- [8. AI-подсистема — «Клиент и выбор провайдера» и «Резервный провайдер»](../../architecture/08-ai-subsystem.md#клиент-и-выбор-провайдера) — логика выбора дословно; активен всегда ровно один провайдер
- [13. Окружения, секреты](../../architecture/13-environments-secrets.md#секреты-vercel-env) — `MISTRAL_API_KEY`, `OPENROUTER_API_KEY`, `OPENROUTER_MODEL`
- [12. Структура репозитория](../../architecture/12-repo-structure.md) — `lib/ai/` и граница «вызовы LLM только через lib/ai»
- [14. Правила вайбкодинга](../../architecture/14-vibecoding-rules.md) — правило 9

Существенные факты:

- Клиент — стандартный OpenAI-совместимый SDK (npm-пакет `openai`) с `baseURL`
  провайдера; отдельные SDK Mistral/OpenRouter не подключать.
- Модель по умолчанию для Mistral в архитектуре не зафиксирована (открытый вопрос
  №2 эпика): завести конфигурируемую константу в `lib/ai/config.ts`
  (предложение — `mistral-small-latest`) с возможностью переопределения параметром
  вызова (источником станет `ai_settings.model`, потребитель — T-05).
- Ретраи здесь не реализуются — ими управляют шаги Inngest (T-05); клиент лишь
  бросает нормализованную ошибку и задаёт разумный таймаут запроса.
- Ключи API не должны попадать в логи и в клиентский бандл: модуль — только
  серверный (`server-only`).

## Шаги реализации

1. `lib/ai/config.ts`: `resolveProvider()` → `{ provider: "mistral" | "openrouter",
   baseURL, apiKey, defaultModel }`:
   - `MISTRAL_API_KEY` задан → Mistral: `baseURL` La Plateforme, дефолтная модель
     из константы;
   - иначе `OPENROUTER_API_KEY` задан → OpenRouter: `baseURL`
     `https://openrouter.ai/api/v1`, модель — `OPENROUTER_MODEL` (не задана вместе
     с ключом → понятная ошибка конфигурации);
   - не задан ни один → понятная ошибка при первом вызове (не при импорте модуля —
     сборка без ключей должна проходить).
2. `lib/ai/client.ts` (`import "server-only"`): функция вида
   `generateCompletion(messages, { model?, temperature?, maxTokens? })` →
   текст ответа; таймаут запроса; нормализованная ошибка (`AiProviderError`
   с кодом/статусом, без утечки ключей в message).
3. Индекс `lib/ai/index.ts` — публичная поверхность модуля (клиент; позже —
   маскирование T-03 и промпт T-04).
4. Юнит-тесты (env подменяется в тестах):
   - оба ключа заданы → Mistral (приоритет);
   - только `OPENROUTER_API_KEY` + `OPENROUTER_MODEL` → OpenRouter с этой моделью;
   - `OPENROUTER_API_KEY` без `OPENROUTER_MODEL` → ошибка конфигурации;
   - ни одного ключа → ошибка при вызове, а не при импорте;
   - переданный параметр `model` переопределяет дефолт.
   Сетевые вызовы в тестах мокаются — живой LLM не дёргать.

## Критерии приёмки

- [ ] Провайдер выбирается строго по логике §8: `MISTRAL_API_KEY` → Mistral, иначе OpenRouter; смешивания нет
- [ ] Один клиент/SDK, различие провайдеров — только `baseURL`, ключ и модель (конфигурация, не код)
- [ ] Модуль серверный (`server-only`); ключи не появляются в логах и сообщениях ошибок
- [ ] За пределами `lib/ai` нет импортов LLM SDK (проверка grep — правило 9)
- [ ] Юнит-тесты из шага 4 написаны и проходят
- [ ] Сборка проходит без задания LLM-ключей
