# T-08. Executive summary — ручные шаги

> Этот тикет выполняет **человек** после завершения всех dev-тикетов эпика.
> Агенты сюда только дописывают шаги. Формат шага: зачем → что сделать → как проверить.

## Предусловия

- Dev-тикеты T-01–T-07 в статусе `done`.
- Эпики E-001 и E-002 завершены: прод на Vercel (fra1), живой вебхук Zernio принят,
  Telegram-канал подключён, сообщения появляются в инбоксе.
- Готовность завести аккаунты Inngest Cloud и Mistral La Plateforme (оплата Mistral —
  по мере использования; у Inngest есть бесплатный тариф).

## Шаги

### 1. Применить миграции генерации и Realtime в dev/prod

- **Зачем:** атомарная финализация черновика и доставка изменений панели через
  Supabase Realtime зависят от двух новых миграций схемы; применять их вручную
  через SQL Editor нельзя (правило 2).
- **Что сделать:** штатным Supabase migration workflow сначала для dev, затем для
  prod применить из репозитория миграции
  `20260722100000_finalize_draft_generation.sql` и
  `20260722110000_enable_drafts_realtime.sql` (проверить целевой project ref,
  `supabase migration list`, затем `supabase db push`). Не копировать SQL в
  Dashboard и не помечать миграции применёнными без фактического выполнения.
- **Проверка:** в каждом окружении `supabase migration list` показывает обе
  миграции применёнными; в `pg_indexes` существует
  `drafts_one_ready_per_conversation_idx`, а в `pg_publication_tables` для
  публикации `supabase_realtime` присутствует таблица `public.drafts`. После
  deploy INSERT/UPDATE черновика приходит в открытую панель без перезагрузки.

### 2. Inngest Cloud: аккаунт и интеграция с Vercel

- **Зачем:** в проде функции `generate-draft`/`regenerate-draft` выполняет Inngest
  Cloud — он должен видеть приложение
  ([13. Деплой](../../architecture/13-environments-secrets.md#деплой): «Inngest
  подхватывает функции через интеграцию с Vercel»).
- **Что сделать:** создать аккаунт на inngest.com → подключить официальную
  интеграцию Inngest в Vercel (Marketplace) к проекту — она сама проставит
  `INNGEST_EVENT_KEY` и `INNGEST_SIGNING_KEY` в env проекта; если делается вручную —
  скопировать оба ключа из Inngest Cloud в Vercel → Settings → Environment
  Variables (Production) и сделать redeploy. Значения ключей никуда не коммитить.
- **Проверка:** после deploy приложение видно в Inngest Cloud (Apps), функции
  `generate-draft` и `regenerate-draft` в списке; тестовое событие из Dev-вкладки
  Inngest доходит до функции.

### 3. Подписать DPA Inngest

- **Зачем:** Inngest — субпроцессор (через него ходят псевдонимные ID); в
  [§15.2](../../architecture/15-compliance-gdpr.md#122-субпроцессоры-и-данные)
  зафиксировано действие «DPA подписать» (риск минимален благодаря правилу
  «только ID», но цепочка должна быть корректной).
- **Что сделать:** запросить/принять DPA Inngest (обычно доступен на сайте в
  разделе Legal/Trust); сохранить копию.
- **Проверка:** подписанный/принятый DPA сохранён в документах проекта.

### 4. Mistral La Plateforme: аккаунт и API-ключ

- **Зачем:** генерация черновиков ходит в Mistral (`MISTRAL_API_KEY`) —
  [8. AI-подсистема](../../architecture/08-ai-subsystem.md#клиент-и-выбор-провайдера).
- **Что сделать:** создать аккаунт на console.mistral.ai, включить биллинг,
  создать API-ключ; добавить `MISTRAL_API_KEY` в Vercel (Production; Preview — по
  желанию) и в локальный `.env.local`; redeploy. OpenRouter-переменные в проде
  не задавать. OpenRouter выбирается **только если `MISTRAL_API_KEY` отсутствует**;
  при наличии Mistral key приложение всегда использует Mistral, и runtime-fallback
  на OpenRouter при ошибке/таймауте Mistral не выполняется. Если OpenRouter нужен
  как осознанный резервный режим, убрать `MISTRAL_API_KEY`, задать
  `OPENROUTER_API_KEY` и `OPENROUTER_MODEL` и отдельно принять его условия §15.2.
- **Проверка:** после redeploy живое входящее сообщение приводит к черновику
  в панели треда (см. финальную проверку); в консоли Mistral виден расход запросов.

### 5. Mistral: DPA и режим без обучения на данных

- **Зачем:** через Mistral проходит контент переписок (после маскирования) —
  требуется DPA и режим no-training
  ([§15.2](../../architecture/15-compliance-gdpr.md#122-субпроцессоры-и-данные)).
- **Что сделать:** проверить актуальные условия La Plateforme: принять/подписать
  DPA, убедиться, что для API-данных действует режим «не обучаемся на данных
  клиентов» (или включить соответствующую настройку), зафиксировать условия
  ретенции запросов. Записать ответы рядом с документами по Zernio.
- **Проверка:** DPA сохранён; настройка no-training подтверждена; ретенция
  зафиксирована. Если условия неприемлемы — остановиться и обсудить
  (Azure OpenAI EU / другой вариант — см. §8).

### 6. Утвердить модель по умолчанию и настройки AI

- **Зачем:** модель по умолчанию в архитектуре не зафиксирована (открытый вопрос
  №2 эпика) — от неё зависят и качество, и стоимость черновиков.
- **Что сделать:** посмотреть текущие модели/цены Mistral; утвердить дефолт
  (предложение тикетов — `mistral-small-latest`; альтернатива — `mistral-large-latest`
  для качества). При отличии от дефолта в коде — выбрать модель в
  Настройки → AI (T-06). Там же выставить тон, язык, подпись, период дебаунса
  (по умолчанию ~45–60 сек) и включить авто-генерацию DM.
- **Проверка:** значения сохранены и переживают перезагрузку страницы; черновики
  генерируются выбранной моделью (поле «модель» у черновика).

### 7. (Опционально) Локальный сквозной прогон с живым ключом

- **Зачем:** проверить контур локально до прода и увидеть критерий «телефон —
  плейсхолдер» в логе промпта.
- **Что сделать:** в `.env.local` задать `MISTRAL_API_KEY` и `AI_LOG_PROMPTS=true`;
  запустить `supabase start` + `next dev` + `npx inngest-cli dev` (+ туннель из
  E-002 для живых вебхуков, либо фикстуры curl'ом); отправить в диалог сообщение
  с телефоном. **В проде `AI_LOG_PROMPTS` не включать** (контент в логах —
  [§15.2](../../architecture/15-compliance-gdpr.md#122-субпроцессоры-и-данные)).
- **Проверка:** в серверном логе промпта вместо телефона — `{{PHONE_1}}`;
  в тексте черновика, если модель его использует, — реальный номер (обратная
  подстановка).

## Финальная проверка эпика

Критерий этапа 2 из [плана внедрения](../../architecture/16-rollout-plan.md#этап-2--ai-черновики-с-дебаунсом-2-3-дня):

1. Открыть тред подключённого Telegram-диалога на проде.
2. С личного Telegram отправить **три сообщения подряд** (в пределах периода
   дебаунса), в одном из них — номер телефона.
3. Пока идёт генерация — в панели «генерируется…»; после паузы появляется
   **ровно один** черновик, отвечающий на все три сообщения, без перезагрузки
   страницы.
4. Локально/в dev с `AI_LOG_PROMPTS=true` (шаг 7) убедиться: телефон в промпт
   не ушёл — виден плейсхолдер.
5. Нажать «сгенерировать заново» — старый черновик заменяется новым (в БД прежний
   помечен `superseded`, `ready` всегда один).
6. «Править» — сохранить правку (статус `edited`), «отклонить» — панель очищается;
   «принять» помечено как «отправка — этап 3».
7. Выключить авто-генерацию в Настройки → AI, прислать сообщение — черновик
   не создаётся; включить обратно.
