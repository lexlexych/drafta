# T-05. generate-draft: дебаунс, пайплайн, supersede, регенерация

## Цель

Inngest-функция `generate-draft` превращает пачку входящих в черновик: дебаунс по
`conversationId` с периодом из `ai_settings.debounce_seconds` (три сообщения подряд →
один черновик после паузы), пайплайн шагами (контекст → маскирование → стоп-чек →
LLM → обратная подстановка → draft `ready`), supersede прежнего `ready`-черновика,
конкурентность `limit: 2` per workspace. Отдельный обработчик без дебаунса выполняет
регенерацию по событию `draft/regenerate.requested`.

Существенные факты:

- T-01 дал serve-роут, схемы событий и скелет функции — этот тикет наполняет её.
  T-02/T-03/T-04 дали клиент LLM, маскирование и сборку промпта — здесь только
  оркестрация, свой LLM-код не писать (правило 9).
- **Период дебаунса** (открытый вопрос №1 эпика): проверить по актуальной
  документации Inngest, поддерживает ли конфиг `debounce` динамический период.
  Если нет — реализовать паттерн: `step.sleep(debounce_seconds из ai_settings)` →
  step «проверить, что `messageId` события всё ещё последнее входящее диалога;
  иначе завершиться без генерации» (выигрывает запуск последнего события).
  Выбранный вариант зафиксировать в отчёте.
- Данные функция достаёт из Supabase в момент выполнения серверным клиентом
  (`SUPABASE_SECRET_KEY`, у функции нет пользовательской сессии) — в событии только ID.
- LLM-классификация по категориям остаётся этапом 6, но существующие категории и
  база знаний уже обязательны: пайплайн использует `category_id` входящего либо
  системную категорию `is_default`, применяет `skip_draft`/`draft_instruction`,
  собирает включённые `kb_files` через существующий token-budget helper и сохраняет
  использованные ID в `drafts.kb_file_ids`. Push-событие (шаг 9) остаётся будущим
  слотом.
- Supersede — строго по §7.2: помечается прежний черновик со статусом `ready`
  (не `edited` — открытый вопрос №4 эпика); пользователь никогда не видит два
  конкурирующих черновика. Рекомендуется закрепить инвариант частичным уникальным
  индексом `unique (conversation_id) where status = 'ready'` — миграцией
  (правило 2), это защитит от гонок.
- Дебаунс нужен только для `kind = dm`; регенерация — без дебаунса (§7.2:
  «для комментариев и email дебаунс не нужен» — комментарии тем не менее этап 5).

## Шаги реализации

1. Конфигурация `generate-draft` (`lib/inngest/functions/generate-draft.ts`):
   триггер `interaction/received`; дебаунс по ключу `conversationId` (см. факты);
   `concurrency: { key: workspaceId, limit: 2 }`; ретраи по умолчанию Inngest.
2. Шаги пайплайна (каждый — `step.run`, ретраится независимо):
   - **load-context**: по `conversationId` загрузить диалог (`kind = dm`),
     `ai_settings`, capabilities `channel_connection`, workspace-scoped `kb_files`
     и назначенную/default категорию; собрать пачку — входящие
     после последнего исходящего сообщения (если исходящих нет — последние N,
     например 20); зафиксировать `first/last message id` диапазона; пачка пуста →
     завершиться;
   - **stop-check**: авто-генерация DM в `ai_settings` выключена либо выбранная
     категория имеет `skip_draft` → завершиться;
   - **mask**: `maskMessages` (T-03) на все текстовые данные промпта: историю,
     базу знаний, настройки и категорию;
   - **create-generating**: создать draft со статусом `generating` (диапазон,
     conversation, `kb_file_ids`) — панель (T-07) показывает «генерируется»;
   - **generate**: `buildDraftPrompt` (T-04) + `logPromptIfEnabled` + вызов LLM
     через `lib/ai` (модель: `ai_settings.model` или дефолт конфига);
   - **finalize**: обратная подстановка (`unmaskText`), одним шагом/транзакцией:
     прежний `ready`-черновик диалога → `superseded`, новый draft → `ready`
     (текст, модель);
   - при исчерпании ретраев LLM-шага — обработчик `onFailure`: удалить
     `generating`-черновик (панель не должна вечно показывать «генерируется»);
     решение зафиксировать в отчёте.
3. Миграция: частичный уникальный индекс на один `ready`-черновик на диалог
   (см. факты).
4. Регенерация: функция `regenerate-draft` на `draft/regenerate.requested` —
   без дебаунса, переиспользует те же шаги (общий модуль пайплайна); прежний
   `ready`/`edited` черновик при регенерации → `superseded` (пользователь явно
   попросил новый); стоп-чек авто-генерации при явной регенерации не применяется.
5. Тесты (LLM мокается подменой `lib/ai`; БД — локальный Supabase):
   - happy path: событие → draft `ready`, диапазон = пачка, модель и использованные
     `kb_file_ids` записаны, KB/категория попали в промпт,
     телефон из сообщения в промпт не попал (мок LLM получил `{{PHONE_1}}`),
     а в тексте черновика (мок возвращает текст с плейсхолдером) — подставлен
     обратно;
   - supersede: существующий `ready` → `superseded`, новый `ready` ровно один;
   - стоп-чек: авто-генерация выключена → черновиков не создано;
   - `edited`-черновик при обычной генерации не трогается;
   - регенерация: `ready` → `superseded`, создан новый; работает и при
     выключенной авто-генерации;
   - payload эмитируемых событий — только ID (типы + тест);
   - пустая пачка (нет новых входящих) → без черновика.
   Для юнит-тестов шагов использовать `@inngest/test` (InngestTestEngine) или
   прямое тестирование вынесенного модуля пайплайна.

## Критерии приёмки

- [ ] Три фикстуры подряд (< периода дебаунса) в один диалог → ровно один черновик после паузы (ручная проверка через Dev Server; см. DoD)
- [ ] Период дебаунса берётся из `ai_settings.debounce_seconds` конкретного workspace
- [ ] В LLM уходит только замаскированный текст; обратная подстановка работает (автотест)
- [ ] Supersede: в диалоге не бывает двух `ready`-черновиков (тест + индекс); `edited` при авто-генерации не трогается
- [ ] Стоп-чек авто-генерации и `category.skip_draft` работает; KB и выбранная/default
  категория реально используются; будущие слоты классификации этапа 6 и push этапа 9
  помечены в коде
- [ ] `concurrency` per-workspace `limit: 2`; payload событий — только ID (правило 7)
- [ ] LLM вызывается только через `lib/ai` (правило 9); `SUPABASE_SECRET_KEY` — только в серверном коде
- [ ] Регенерация без дебаунса создаёт новый черновик и supersede'ит прежний
- [ ] Все тесты шага 5 написаны и проходят

## 🔧 Отчёт разработчика

### Что сделано

- `lib/inngest/functions/draft-pipeline.ts`: реализован общий тестируемый пайплайн
  генерации и регенерации. Для обычного события период загружается из
  workspace-scoped `ai_settings`, выполняется durable `step.sleep`, затем
  last-event check; старые события завершаются без черновика. Контекст и все
  запросы защищены фильтрами `workspace_id`/`conversation_id`; пачка ограничена
  последними 20 сообщениями и начинается после последнего исходящего.
- Пайплайн напрямую переиспользует существующие `listKnowledgeFiles`,
  `listCategories`, их текущие типы и `buildKnowledgeBaseContext`: включённые
  `kb_files` попадают в промпт в детерминированном бюджете 24 000 токенов, а
  `usedFileIds` записываются в `drafts.kb_file_ids`. Для категории используется
  `category_id` сообщения, иначе существующая `is_default`; применяются
  `skip_draft`, описание и `draft_instruction`. Пустая KB безопасна, отсутствие
  обязательной default/назначенной категории даёт явную ошибку без LLM-вызова.
- Все текстовые входы промпта (история, KB, настройки, категория) маскируются
  общим вызовом `maskMessages`; затем вызываются контракт T-04
  `buildDraftPrompt`/`logPromptIfEnabled` и единая точка `generateCompletion` из
  `lib/ai`, после чего ответ восстанавливается через `unmaskText`. Выбор
  провайдера не менялся: runtime fallback отсутствует, OpenRouter выбирается
  существующим клиентом только при отсутствии `MISTRAL_API_KEY`.
- `lib/inngest/functions/generate-draft.ts` и `index.ts`: зарегистрированы
  `generate-draft` и `regenerate-draft`, общий workspace concurrency `limit: 2`
  (`scope: env`) плюс сериализация одного conversation; регенерация не ждёт
  debounce и игнорирует только флаг auto-generation. Оба `onFailure` очищают
  оставшиеся `generating`-черновики. Payload событий не расширялся и содержит
  только ID.
- `supabase/migrations/20260722100000_finalize_draft_generation.sql`: добавлен
  частичный уникальный индекс одного `ready` на conversation и RPC, которая под
  блокировкой conversation атомарно supersede'ит прежний `ready`, публикует новый
  draft, а при явной регенерации также supersede'ит `edited`. Миграция сначала
  детерминированно нормализует возможные старые дубли.
- Добавлены `lib/inngest/functions/draft-pipeline.test.ts`,
  `lib/draft-generation-migration.test.ts`; расширен
  `app/api/inngest/route.test.ts`. Покрыты три события/один победитель,
  masking → prompt → restore, реальная передача KB/category, сохранение KB IDs,
  stop-check, `skip_draft`, assigned/default category, пустая пачка,
  регенерация без debounce при выключенной auto-generation, supersede-контракт,
  concurrency/onFailure и регистрация обеих функций.

### Отклонения от исходного плана

- Нативный `debounce.period` установленной Inngest v4 — статический `TimeStr`,
  поэтому динамический период из БД реализован согласованным паттерном
  `step.sleep(debounce_seconds)` → last-event check. Это сохраняет требуемую
  семантику per-workspace и проверено без живого Inngest.
- По прямому решению пользователя старые формулировки «KB/category вне скоупа»
  заменены реальной интеграцией с уже существующими сущностями; новых таблиц,
  моделей или параллельных репозиториев для KB/category не создано.
- `supabase db reset` и ручной Docker/Inngest Dev Server smoke не запускались по
  прямому решению пользователя. SQL-инварианты проверены контрактным тестом,
  pipeline — полностью мокированными unit/integration-style тестами без сервера.

### Вне скоупа и открытые вопросы

- LLM-классификация неприсвоенных сообщений остаётся этапом 6; до неё используется
  существующая системная категория по умолчанию. Push после готовности остаётся
  этапом 9 и помечен TODO.
- Docker/Inngest smoke можно выполнить позднее как необязательную окруженческую
  проверку; функциональных блокеров или ручных шагов для T-05 нет.
