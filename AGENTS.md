# AGENTS.md — правила для AI-агентов проекта drafta

Единая точка входа для любой агентной среды. Codex CLI читает этот файл нативно;
Claude Code подключает его через `CLAUDE.md` (импорт `@AGENTS.md`).

## О проекте

SaaS AI-инбокс (PWA) для малого бизнеса: переписки и комментарии из мессенджеров и
соцсетей в одном месте + автоматические AI-черновики ответов. Рынок запуска —
Германия/ЕС, GDPR заложен в архитектуру с первого дня. Стек: Next.js, Supabase
(Frankfurt), Vercel (+ Workflows), Serwist, Zernio, Postmark, Mistral
(резервный LLM-провайдер — OpenRouter).

Вся архитектура — в `docs/architecture/` (оглавление: `docs/architecture/_index.md`).
Перед любой работой с кодом обязательны:

- `docs/architecture/02-glossary.md` — глоссарий; термины обязательны в коде и текстах;
- `docs/architecture/14-vibecoding-rules.md` — полный список правил вайбкодинга;
- глава архитектуры, относящаяся к текущей задаче.

## Язык

Общение с пользователем и проектная документация — по-русски. Код, идентификаторы,
имена файлов и сообщения коммитов — по-английски.

## Жёсткие правила (кратко)

Полный список с обоснованиями — `docs/architecture/14-vibecoding-rules.md`:

1. Тенант всегда `workspace`, никогда `account` (глоссарий §2).
2. Схема БД меняется **только** миграциями в `supabase/migrations/`, не через дашборд.
3. Каждая новая таблица — сразу с `workspace_id`, RLS-политиками и каскадом от workspace.
4. Провайдер-специфичный код — только в `lib/channels/`; ядро видит только нормализованные типы.
5. `SUPABASE_SECRET_KEY` — только в серверном коде.
6. Вебхук-роуты не вызывают LLM и отвечают < 1 сек; тяжёлая работа — прогоны Workflows.
7. Аргументы запуска прогона — **только ID**, никогда персональные данные.
8. Любая внешняя отправка — прогоном с ретраями, не из запроса.
9. Вызовы LLM — только через `lib/ai` (с маскированием), SDK напрямую не дёргать.
10. Auth-письма шлёт Supabase через Postmark-SMTP — свой код отправки инвайтов не писать.
11. Новые внешние сервисы — только с обновлением списка субпроцессоров (§15).
12. После каждой фичи — прогон smoke-тестов.

## Агентский workflow: эпики и тикеты

Разработка ведётся эпиками; эпик состоит из тикетов и живёт в `docs/epics/epic_NN/`.
Полное описание процесса, ролей и статусов — **`.ai/workflow.md`** (обязателен к
прочтению перед работой по командам ниже). Текущее состояние проекта —
**`docs/epics/STATUS.md`**.

| Команда | Что делает | Процедура |
|---|---|---|
| `/createEpic <описание \| этап N>` | создать эпик с тикетами (агент-аналитик) | `.ai/commands/createEpic.md` |
| `/startEpic E-NNN` | выполнить эпик: по каждому тикету разработчик → ревьюер | `.ai/commands/startEpic.md` |
| `/finishEpic E-NNN` | финализировать эпик после ручных шагов: статусы + merge в `main` | `.ai/commands/finishEpic.md` |

**Правило перехвата команд:** если сообщение пользователя начинается с `/createEpic`,
`/startEpic` или `/finishEpic` (со слэшем или без, в любом регистре) и среда не
обработала его как встроенную команду — прочитай соответствующий файл из
`.ai/commands/` и выполни процедуру; остаток сообщения — аргументы.

**Git-политика** (полностью — `.ai/workflow.md`, раздел «Git-политика»): ветка на эпик
`E-NNN` — её создаёт `/startEpic` от `main`; вся работа эпика коммитится только в неё
с префиксом `[E-NNN/T-NN]`; `main` продвигается только merge-коммитами эпиков через
`/finishEpic`; ветки не переключать самовольно, push — только по просьбе человека.

**Правило: смёрженный PR — законченный.** После мёржа PR его ветку **нельзя
переиспользовать** для доработок. Пуш новых коммитов в такую ветку не меняет уже влитый
PR и **не попадает в `main`** — коммиты «повисают» мимо `main`, и на проде остаётся старый
код. Любая доработка/фикс после мёржа — это **новое изменение**: создать **свежую ветку от
актуального `main`** (`git fetch origin main && git checkout -B <новая-ветка> origin/main`),
перенести туда правку (`git cherry-pick <sha>` или заново) и открыть **новый PR**. Никогда не
наслаивать follow-up на уже влитую историю ветки. Перед доработкой всегда проверять статус PR
исходной ветки (`merged`?) и актуальный `origin/main`.

Роли агентов описаны в `.ai/roles/` (analyst, developer, reviewer):

- **Среда с суб-агентами (Claude Code):** роли запускаются изолированными
  суб-агентами `epic-analyst`, `ticket-developer`, `ticket-reviewer`
  (определения — `.claude/agents/`), строго последовательно и синхронно.
- **Среда без суб-агентов (Codex CLI):** одна сессия исполняет роли последовательно,
  перед каждой читая её файл из `.ai/roles/` и опираясь только на файлы
  (тикеты, код, документация), а не на память о предыдущих ролях.

Устройство и настройка workflow — `.ai/README.md`.
